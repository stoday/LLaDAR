# PRD：由 Agent 選用生成工具的問答測試集

- [三欄資料契約](PRD-simple-agent-evaluation.md)、[題型契約](PRD-question-type-test-dataset.zh-TW.md)、[評估需求契約](PRD-evaluation-criteria.zh-TW.md) 繼續適用。
- 歷史 PRD 的工具限定及禁止直接修改結果等條文，不得用來覆蓋本案明確保留的 Python 自主處理能力。

## 問題與實際觀察

目前主程式固定執行知識點擷取、語意圖譜與測試計畫階段。即使使用者的 Skill 要求依序閱讀文章、辨識完整知識段落並直接生成問答，也必須提交圖譜才能繼續。

2026-10-07 的 [實際 log](../logs/other_project_log/log-20261007.txt) 顯示：

1. Agent 一次讀完文章，提交 8 個有原文引用的知識點。
2. 圖譜階段接受了 `nodes`、`edges`、`facts` 均為空清單的圖譜。
3. 題目規劃階段使用 Python 找到執行中的 `GenerationWorkspace`，直接補入圖譜節點與事實。
4. 提交 8 題成功後發生 `GraphRecursionError`；重試再次提交時得到「已提交」，最後仍完成輸出。

這個案例同時顯示固定流程與 Skill 方法衝突、空圖譜驗證不足，以及成功交付後的重試缺乏完成狀態辨識。Agent 用 Python 自主補救的能力是要保留的產品選擇，不是本案要移除的功能。

## 產品目標

- Skill 描述生成方法；Agent 按 Skill、使用者選項與來源內容選用工具，主程式不強制每次建立圖譜。
- 一般問答可由來源段落直接生成，沒有圖譜仍可成功。
- 原有圖譜偵測能力保留；選用圖譜時，正式輸出前須通過實質驗證。
- 保留目前 Python 探索、計算、檔案處理與直接調整執行中結果的能力，不要求全部由工具提交。
- 不以操作途徑判斷結果是否有效；工具提交與 Python 處理的候選都由同一套最終驗證判定。
- 維持三欄 JSONL 與既有 run-agent、eval、report 的使用方式。

## 範圍與非目標

本案包含生成流程、生成工具、結果收集與最終驗證、重試完成狀態、生成紀錄，以及 Skill 範本與作者指南的調整。

本案不新增 Python 隔離、限制 Python 只能計算、或強制所有結果經工具提交。不新增圖資料庫、Skill 安裝管理、多 Skill 排程或新的生成策略旗標；不重構受測 Agent 執行、eval 評分方法或 report 統計語意。

## 使用者體驗與方法選擇

既有指令保留：

```powershell
lladar create test-dataset --knowledge .\Knowledge --output outcome
lladar create test-dataset --knowledge .\Knowledge --skill .\test-dataset-skill --output outcome
```

- `--skill` 指定的方法是生成指引；不要求額外 manifest 或圖譜宣告旗標。
- 主程式提供來源讀取、知識整理、問答交付與圖譜能力。工具可用不代表必須呼叫。
- Skill 明確要求直接問答時，Agent 直接產題，不得因主程式階段限制而被迫建立圖譜。
- Skill 明確要求圖譜偵測時，Agent 必須準備有效圖譜與對應測試資訊；不能省略圖譜而宣稱完成該方法。
- Skill 未限定方法時，由 Agent 選擇並記錄實際方法及理由；理由是執行摘要，不要求揭露內部推理。
- 為維持既有預設用途，內建 Skill 保留來源事實題與來源支持的圖譜偵測指引；這是內建方法的指引，不是所有自訂 Skill 的強制階段。沒有適合的圖譜偵測內容時可輸出一般問答，記錄原因。
- 明確指定受控變體選項時，須產生並驗證所需圖譜、維度與配對；無法滿足時明確回報，不可悄悄忽略選項。
- 既有 `--count`、`--question-type`、`--model`、`--log`、輸出路徑與覆寫行為保留。不新增綁定特定模型供應商的圖譜流程。

## 生成流程

```text
載入選定 Skill 與來源
        ↓
Agent 依序讀取、辨識有意義的知識段落
        ↓
依 Skill 與任務選擇工具，可使用 Python 自主處理
        ├─ 直接生成問題、答案與原文證據
        └─ 建立圖譜 → 生成事實題、概念映射或受控變體題
        ↓
收集最終候選結果與方法紀錄
        ↓
固定結果快照 → 最終驗證 → 去重、套用數量上限
        ↓
寫入三欄 JSONL 與適用的 sidecar
```

同一次生成可以包含直接問答與圖譜題目。每筆資料記錄自己的生成方法與證據，不以整份資料集只有一種方法為前提。

主程式可保留來源分頁、工作預算與必要的先後依賴，但不得用固定 `semantic_graph` 階段作為一般問答的完成條件。依賴圖譜的測試仍須取得有效圖譜內容才能通過驗證。

## 一般問答方法

- 依文章順序閱讀；知識單位是可完整回答的事實、規則、流程或概念，不要求每句都是一個原子知識點。
- 允許合併相鄰段落，以保留主體、條件、例外及解釋。
- 問題可獨立理解，答案由來源支持；保留數值、單位、否定與必要條件。
- 每筆問答附原文引用與來源位置；不需要圖譜節點、概念 ID 或圖譜測試計畫。
- 每段產幾題及是否略過由 Skill 定義。若 Skill 要求一段一題，記錄知識段落至題目的對應；有數量上限、去重或略過時記錄原因，不把輸出數字相同當成一對一證明。
- 選擇與排序題仍遵守來源支持的候選集合及既有答案協定，不因取消圖譜必經而放寬。

## 圖譜能力與實質驗證

圖譜工具應提供建立或提交、讀取與驗證圖譜的能力，回傳可引用的節點與事實。沿用現有契約時可保留工具名稱；實作不得只更名而保留圖譜必經限制。

最終圖譜驗證至少檢查：

1. 圖譜有實際可用內容；三個空清單不是有效圖譜，不能作為圖譜方法完成的證據。
2. 節點 ID 唯一，節點、邊、事實與證據引用有效，所引用的原文與位置能對照實際載入來源。
3. `source`、`inferred` 與 `synthetic_control` 的來源類別維持既有語意；推論概念有成員與支持依據。
4. 每個圖譜題目引用存在且有效的圖譜內容，答案契約與候選一致。
5. 概念映射有足夠且可比較的成員；受控變體符合已宣告維度、條件與完整配對。
6. 只輸出一般問答時可沒有圖譜；宣稱圖譜已使用或交付圖譜時，圖譜不可省略驗證。選用圖譜但無可用內容時須明確報錯或記錄放棄該方法，依 Skill 與使用者要求決定是否可繼續。

圖譜不要求每份來源都出現推論概念或關係邊。有效的直接事實圖譜可以沒有概念；一般問答也不必為了補圖譜而創造概念。

格式與引用驗證不等於機器已證明所有自然語言主張正確。語意檢查須說明其實際方法與限制，不把引用存在當成答案必然正確。

## Python 自主處理與結果交付

- 保留現有 Akasha Python 能力與執行方式，允許 Agent 探索環境、讀取可用程式、執行程式及直接調整候選結果或執行中的生成資料。
- 不把「全部由工具提交」作為成功條件；既有提交工具仍是方便且可立即得到驗證回饋的選項。
- 主程式須提供明確的結果收集契約：既有工作區候選，以及執行前指定的候選檔案交付位置，都能被收集成相同內部結果。不得掃描任意目錄猜測哪一份是本次輸出。
- Python 產生的候選仍需題目、答案、來源證據與適用的圖譜／probe 資訊，不能只靠自然語言「已完成」判定成功。
- 最終收集時複製並固定候選結果及證據快照；驗證與正式寫檔使用同一份快照，不在驗證後重新讀取可能已改變的工作區。
- 最終驗證重新檢查快照，不沿用先前的 `accepted` 作為免驗證證明。直接修改圖譜後，也必須驗證修改後的圖譜。
- Agent 可以直接寫候選檔案，但既有檔案保護、`--force` 及正式輸出路徑規則仍適用於 LLaDAR 的發布；不能以候選檔案存在就回報正式成功。

## 完成、失敗與重試

- 完成條件是存在符合所選方法與使用者選項的最終候選結果，且通過最終驗證，不是每個預設階段都曾呼叫工具。
- 模型或 Agent 在交付後發生輪數上限等錯誤時，先收集並驗證已完成的結果，再決定是否重試。
- 已有有效結果時不要求重新提交同一份資料；保留模型錯誤紀錄，明確區分「Agent 執行發生錯誤」與「產物驗證成功」。
- 候選不完整或驗證失敗時，回傳可修正的具體錯誤，在既有有限重試預算內補救。不能因重試而移除圖譜或配對要求。
- 重複交付須可識別；不得重複增加題數、覆蓋已完成結果或產生孤立的配對題。
- 最終驗證失敗不得標示 `complete`；保留錯誤及執行紀錄，避免留下被當成正式成功的部分產物。

## 輸出與下游相容性

正式 JSONL 每列仍只有：

```json
{"question": "梅澤捨次郎的原名為何？", "expected_answer": "秋田捨次郎", "actual_response": null}
```

- `<dataset>.generation.json` 保存來源證據、逐題生成方法、知識段落對應、適用的圖譜／probe 資訊及實際錯誤與修正紀錄。
- 直接問答不偽造圖譜 ID 或 probe 契約；只有有效圖譜被採用時才輸出 `<dataset>.graph.json`，不寫空圖譜作為占位。
- 紀錄最終產物的驗證結果與雜湊；不能讓工具事件中的早期接受狀態取代最終產物狀態。
- 逐題方法紀錄與評測 probe 類型分開：經圖譜生成的直接事實題仍可按一般答案正確性評估。
- run-agent 保留問題送出方式、實際回答，以及既有題型／probe 資訊傳遞與指紋核對。
- eval 不直接讀完整圖譜；一般問答使用問題、預期答案與實際回答，圖譜 probe 仍使用 run sidecar 的有效候選與配對契約。
- report 繼續讀取 eval 結果，不新增讀取原始圖譜的必要條件。
- 本案不要求改寫 eval/report 架構；只做必要相容性調整與驗證。若 generation sidecar 結構需升版，須同步調整讀取器，不讓版本變更使現有 probe 悄悄退回一般評分。
- 舊的有效圖譜資料集及其 run snapshot 應繼續可評估；不因本案要求全部重新生成。

## 實作與驗證順序

1. 定義共同候選結果與收集契約，將圖譜依賴改成逐題需求。
2. 取消主程式強制圖譜階段，接入直接問答交付路徑並保留現有圖譜能力。
3. 加入快照式最終驗證與完成狀態辨識，涵蓋工具及 Python 直接處理結果。
4. 更新生成 sidecar 與必要讀取器，驗證既有圖譜資料和無圖譜資料的相容性。
5. 同步 Skill、範本與文件，執行有實質意義的聚焦測試及兩種方法的真實模型驗收。

本案驗收應直接覆蓋實際 log 的三個情境：空圖譜、Python 補救後的最終驗證，以及提交成功後的執行錯誤。測試不得以禁止 Python 取代已確認的產品需求。
