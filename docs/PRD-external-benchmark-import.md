# 外部測試資料集自動匯入與通用案例評分

## Status

核心流程已實作並完成公開 CLI 驗證。Akasha Agent 可從公開 GitHub 或本機來源建立通用案例 bundle；待測 Akasha Agent 已實際回答 BBQ 與 BOLD，封存評分與 `eval --from` 獨立探索皆得到有效結果。匯入器記錄來源證據、無法重現的指標、資料列錯誤與生成設定；評分器核對來源與轉換方案摘要。

目前能力邊界：BBQ 的 `bias_score` 仍列為有來源證據的 `unsupported`，BOLD 的生成指標可對實際回答計算，但待測 Agent 的生成條件尚無法證實與論文相同，報告標為 `not_established`。來源讀取目前支援 JSON、JSONL、CSV；其他格式需擴充受控轉換器。

## Problem Statement

使用者想用 lladar create dataset --convert-from <來源> 直接取得外部測試資料集，接著用 run-agent 和 eval 測試自己的 Agent。目前 create test-dataset 產生的是原題、資訊省略與同儕提示變體的 question group；公開 schema v2、執行器和 BFS 評分都以此結構為前提。外部資料集可能是單選、多選、排序或自由回答，也可能是沒有逐題標準答案、只提供提示讓模型生成文字，再以群組指標評估輸出的資料集。把它們硬塞成 question group 會改變原題意，無法可靠重現來源評分；每遇到一份新資料集都要求人手讀 repo、寫轉換器和評分器，也無法達成自動匯入。

## Solution

新增一條通用 benchmark case 工作流程。使用者只提供公開 GitHub repo URL 或本機目錄；匯入 Agent 自動取得來源、辨識題目與可信評分依據、撰寫轉換程式並在隔離工作區驗證，最後輸出固定且可擴充的案例 artifact、資料集 manifest、版本化評分方案與匯入診斷。評分方案指向經驗證的內建規則、來源規準或 Agent 生成的受控評分器。一般 eval 使用封存方案以便重跑；使用 eval --from <來源> 時，評分探索 Agent 則讀取固定版本的來源，自行重建並驗證評分方案，再對先前待測 Agent 的回答評分。使用者可直接以 run-agent 收集待測 Agent 的真實回答，再以 eval 取得逐題結果、覆蓋率，以及有來源證據且可重現的原始指標。來源有效但欠缺可依循的評分方法，或來源方法互相牴觸時，以 unsupported 明示；讀取故障、來源資料損壞、模型無法判斷與評分器驗證失敗使用各自的錯誤狀態，不由匯入 Agent 編造答案或評分規則。BBQ 與 BOLD 必須由同一套通用匯入 Agent 分別從原始 repo 自行發現資料、任務形式及評分依據，不能由實作者預先餵給它來源對照表。

既有 schema v2 question group、create test-dataset、執行及 BFS 評分維持可用。新工作流程採用獨立、固定版本的通用案例 artifact 契約，並透過同一套公開 artifact 驗證入口依版本與 artifact 類型分派；不為每個來源建立新的案例 schema。

## User Stories

1. 身為測試者，我想用一個 --convert-from 參數指定公開 GitHub repo，省去手動下載與尋找資料檔。
2. 身為測試者，我想以相同指令指定本機目錄，能匯入已取得的資料。
3. 身為測試者，我想在沒有額外必填參數時得到安全、無碰撞的預設輸出位置，且命令印出實際路徑，能立即開始測試與保存產物。
4. 身為測試者，我想看到匯入進度、發現的資料檔與結論，而 JSON/JSONL 輸出仍可供程式讀取。
5. 身為測試者，我想知道使用了哪個 Git commit 或本機來源快照，能重現同一次匯入。
6. 身為測試者，我想保留原始題目、脈絡、選項與作答條件，避免轉換改變測試意義。
7. 身為測試者，我想把單選題轉成有穩定選項 ID 與唯一標準答案的案例，能客觀評分。
8. 身為測試者，我想把多選題轉成答案集合，能依來源規則處理全對或部分給分。
9. 身為測試者，我想把排序題轉成有序答案，能依來源規則處理順序與部分給分。
10. 身為測試者，我想把自由回答題轉成有參考答案或明確規準的案例，能採用來源支持的評分方式。
11. 身為測試者，我想讓評審模型只依來源明確給出的自由回答規準判分，並保存規準、模型資訊和判斷理由。
12. 身為測試者，我想在來源缺少可信標準答案或規準時看到 unsupported 與具體理由，避免虛假的分數。
13. 身為測試者，我想在部分題目無法匯入時仍能執行其餘題目，並看到可執行覆蓋率。
14. 身為測試者，我想讓來源論文、文件與評分腳本有衝突的指標獨立標記 unsupported，而仍能使用可信的逐題標準答案。
15. 身為測試者，我想知道來源規則是從哪份文件、資料欄位或腳本推得，能審查評分依據。
16. 身為測試者，我想保留資料集分類、條件和分組資訊，能計算來源要求的分組指標。
17. 身為測試者，我想讓 LLaDAR 自動驗證匯入 Agent 生成的轉換程式，避免產出無效 artifact 卻顯示成功。
18. 身為測試者，我想重跑已保存的轉換程式並比較結果，能分辨來源變更與匯入程式變更。
19. 身為測試者，我想在同一份案例資料上使用 run-agent，讓待測 Agent 透過其真正的公開輸入介面回答。
20. 身為測試者，我想只把題目與必要的中性格式提示提供給待測 Agent，避免標準答案或評分規準洩漏。
21. 身為測試者，我想保存待測 Agent 的原始回答及解析後答案，能追查選項解析或格式問題。
22. 身為測試者，我想在回答無法唯一解析時看到獨立的無法評分狀態，避免被誤算成答錯。
23. 身為測試者，我想逐題查看正確性、給分、執行錯誤、缺答及無法評分原因，能定位失敗。
24. 身為測試者，我想同時查看通用逐題結果與可重現的來源原始指標，能在不同資料集與原論文之間對照。
25. 身為測試者，我想知道每個分數所用的資料母體與排除數，避免把部分匯入的結果誤當完整 benchmark。
26. 身為測試者，我想保留來源授權與歸屬資訊，能判斷匯入 artifact 的使用條件。
27. 身為測試者，我想在來源不受支援、下載失敗、轉換失敗或評分失敗時取得可讀診斷與非成功退出碼，能修正問題。
28. 身為既有 LLaDAR 使用者，我想繼續使用 schema v2 question group 與 BFS 報告，避免新功能改變現有結果。
29. 身為後續維護者，我想以同一個通用案例契約接入新資料集，無須替每個 repo 增加特製 schema。
30. 身為後續維護者，我想用單選、多選、排序、自由回答四種不同來源形狀驗收整條 CLI 流程，確保基本題型都能執行與評分。
31. 身為測試者，我想讓 LLaDAR 的匯入 Agent 自行處理 BBQ 與 BOLD 兩個原始 repo，藉由實際產物驗證它能辨認不同 benchmark，而非只支援單一格式。
32. 身為測試者，我想測試沒有逐題金標的開放式生成資料集，能以來源定義的輸出指標而非虛構正確答案評估。
33. 身為測試者，我想在兩次乾淨、獨立的匯入中只提供來源 URL，能證明成功來自 Agent 的探索與轉換能力，而非先前快取、手寫對照表或隱藏提示。
34. 身為測試者，我想區分「正確標記 unsupported」與「真的完成來源評分」，避免把整份 BOLD 跳過卻宣稱泛用性驗證通過。
35. 身為測試者，我想讓生成案例依來源要求記錄抽樣次數、停止條件與可控制的生成參數，能判斷來源指標是否可比。
36. 身為測試者，我想讓資料集隨附經驗證的評分方案與評分器，讓 eval 在不重新讀取 repo 的情況下知道如何判分。
37. 身為測試者，我想在評分器遺失、版本不合或摘要被改動時讓 eval 停止評分並說明原因，避免套用錯誤規則。
38. 身為測試者，我想從報告查到每項指標使用的來源依據、評分器版本與參數，能獨立重跑及審查結果。
39. 身為測試者，我想在完成 run-agent 後使用 lladar eval --from <來源>，讓 LLaDAR 的評分探索 Agent 自行讀取該 repo 的評分方法。
40. 身為測試者，我想在同一工作區只有一筆可辨識的待評執行時省略其他參數；若有多筆，命令應列出候選並要求指定，不得猜測要評哪一筆。
41. 身為測試者，我想讓重新探索的評分方式與匯入時封存的方案互相比對，當兩者衝突時看見證據，而不是被靜默改分。
42. 身為測試者，我想在 BBQ 與 BOLD 上使用相同的自動探索、驗證、執行與報告流程，同時保留各自的來源指標名稱、分母與意義。
43. 身為測試者，我想知道 create dataset 和 eval --from 各自把評分方案封存在哪裡，能直接檢查、複製及重跑。
44. 身為測試者，我想在 repo 無法下載、指定版本遺失或檔案無法讀取時看到來源讀取失敗與可重試資訊，而不是收到資料集不支援的結論。
45. 身為測試者，我想在來源資料格式錯誤、欄位缺失、金標無效或 metadata 損壞時看到可定位的來源資料錯誤，而不是讓匯入 Agent 補造資料。
46. 身為測試者，我想在模型經有限修復仍無法可靠辨識題型或評分規則時看到 Agent 判斷未完成，能換模型或重跑而不誤認為來源壞掉。
47. 身為測試者，我想在少數壞資料列與可用資料列共存時保留可用案例，並清楚看到剔除數與原因。
48. 身為測試者，我想在任一階段失敗時保留診斷、工具軌跡與安全的重試入口，且不產生看似成功的殘缺資料集或分數。

## Implementation Decisions

1. 公開匯入介面為 lladar create dataset --convert-from <來源>；來源限公開 GitHub repo URL 與本機目錄。命令預設產出無碰撞、可攜帶的資料集 bundle，內含案例、manifest、評分方案及所需評分器。run-agent 對新版本保存含資料集識別、來源版本與答案位置的執行紀錄；eval 可明確接收 bundle 與答案，也可用 --from <來源> 選擇評分探索模式。只給 --from 時，只有工作區內唯一可辨識且來源相符的已完成執行才能自動選取；零筆或多筆均要求明確指定執行紀錄。既有 schema v2 JSONL 命令用法仍可使用。命令可提供覆寫輸出、模型、憑證檔、工具呼叫上限等可選設定，預設不覆寫既有 artifact。來源無法解析時直接報錯，不產生空的成功結果。
2. GitHub 來源由受控下載步驟取得並固定到實際 commit；本機來源建立可驗證的檔案清單與內容摘要。兩者都記錄取得時間、來源識別、授權資訊、參與轉換的檔案及來源版本。來源更新不靜默改寫先前結果。
3. 匯入 Agent 重用既有 run-agent 的 coding agent 控制、模型設定，以及列目錄、讀檔、搜尋、寫入與重跑 harness 等工具能力；另由受控下載步驟取得 GitHub 來源，再以專用提示及權限進行資料集探索、轉換與評分。它不能修改原始 repo、待測專案或公開輸出以外的路徑。
4. 外部 repo 的下載、產題、評分或安裝腳本只作為可引用的文字證據，首版不執行。由匯入 Agent 生成的轉換及評分程式在隔離工作區執行，不帶入使用者憑證，並受路徑、時間、資源與網路邊界約束。必須執行來源程式才能取得題目或評分的部分標記 unsupported。
5. 新增固定的 schema_version 3 通用 benchmark artifact family，包含資料集 manifest、case record、observed answer、評分方案、逐題評分與 report；使用現有集中式 artifact 驗證機制按版本和類型選擇契約。schema 驗證評分方案的欄位、引用及型別，但不承載任意演算法原始碼，也不單憑 schema 宣稱來源評分正確。既有 schema v2 的 record 形狀與 BFS 語意不被重新定義；新版本不要求舊資料自動轉換。
6. 通用 case record 包含穩定 ID、ready／unsupported 狀態、來源定位、題型、提供給 Agent 的脈絡／題目／選項或生成提示、可選的標準答案或規準引用、逐題或跨案例評分方式，以及可擴充的來源命名空間 metadata。未知頂層欄位仍需拒絕；資料集特有欄位只放在有界且命名清楚的 metadata。
7. 單選使用一個選項 ID；多選使用不重複的選項 ID 集合；排序使用不重複的有序選項 ID；自由回答使用來源支持的參考答案、可執行比對規則或評分規準。各題型都允許來源明確規定的部分給分；沒有足夠規則時不自行預設有爭議的評分法。另支援開放式文字生成案例：原始提示可能是不完整的文字前綴，沒有逐題正確答案；只有在來源定義的輸出指標可驗證時才列為可評案例。
8. 原始題意與選項順序保留。選項題僅在輸出格式不足以可靠解析時，才可加入中性的作答格式提示，並在 manifest 記錄提示內容；不得加入標準答案、來源規準或引導性提示。開放式生成的文字前綴須原樣交給待測 Agent，不得附加問答或 JSON 格式指令。解析結果與原始回答分開保存，無法唯一解析列為 unscorable。
9. 生成的轉換器及評分器須持久保存版本、摘要和來源依據，對固定來源快照能確定性重跑。匯入成功前須驗證 schema、ID 唯一性、選項與答案相容性、來源欄位對應、資料列計數、來源提供的樣本及標籤、重跑一致性；不通過的資料列不得列為 ready。
10. unsupported 只表示來源有效但某題型或評分方法在目前能力與證據下無法可靠支援，須有原因碼、可讀理由和可定位的來源證據。資料列、評分規則與聚合指標可分別 unsupported；來源損壞、讀取失敗與 Agent 判斷未完成各有獨立狀態。局部問題不使其他可信案例失效；整份資料集沒有可執行案例時，命令不能宣稱匯入成功。
11. run-agent 依 artifact 類型分派：既有 question group 沿用目前流程；通用案例依來源任務規則對穩定案例 ID 執行真實目標 Agent 呼叫，生成案例可要求多次獨立抽樣，且每次回答須有可追溯的 sample ID。待測 Agent 的工具、模型與資料仍由其專案公開介面控制；匯入器的參考答案不進入執行環境。
12. eval 依 artifact 類型分派：既有 question group 沿用 BFS；通用案例先核對資料集、執行紀錄與回答的識別及摘要，再對齊 ID、驗證回答。一般模式從資料集 bundle 載入封存評分方案與評分器；--from 模式則啟動評分探索 Agent，讀取與執行紀錄綁定的來源版本，自行生成並驗證評分方案。有逐題規則者計算逐題分數，只有輸出指標的生成案例則計算具來源證據的案例或群組指標。兩種模式都不得臨時猜測缺失的規則或直接執行來源 repo 程式。
13. 自由回答若來源有明確規準但無可執行評分程式，可使用評審模型；每次判斷須保存規準版本、模型、輸入依據、分數與理由。規準不足、評審失敗或結果不符合契約時列為 unsupported 或 judge_error，不混入有效分數。
14. 報告區分來源題目總數、ready、unsupported、已執行、執行錯誤、缺答、無法解析與有效評分數；每項指標附計算母體、排除條件、來源依據與評分器版本。來源規則互相牴觸時，受影響的聚合指標標記 unsupported 並列出衝突，可信的逐題結果仍可輸出。
15. BBQ 與 BOLD 均由相同的通用匯入 Agent 以原始 repo 為唯一資料集輸入，並在乾淨工作區各自執行。Agent 必須自行判定每份來源是選項題、開放式生成或其他型態，找出所需資料與評分依據，生成轉換及評分實作。產品程式、匯入提示與預置工具不得含 BBQ 或 BOLD 專用對照表；來源專用的驗收檢查可由獨立測試端執行，但不得回饋給匯入 Agent。
16. manifest 須記錄來源要求的抽樣次數、生成長度、停止條件與其他影響評分的生成設定；實際執行紀錄須記錄能否控制這些設定。待測 Agent 若無法遵守必要的來源生成協定，該來源指標應標示不可比或 unsupported，不得以表面上有文字輸出代替來源方法。
17. 匯入 Agent 須為每項可評結果產出評分方案描述：規則 ID、適用題型與範圍（逐題或跨案例）、所需答案與來源 metadata、正規化及排除方式、分母、參數、來源證據，以及受控評分器的版本與內容摘要。case 只引用規則 ID；資料集 manifest 保存規則表與所有相對於匯入產物的評分器引用，移動整份產物後仍能重跑。
18. 通用評分方案可指向 LLaDAR 已驗證的確定性規則、來源支持的自由回答規準，或匯入 Agent 生成並驗證的隔離評分器。來源專有的聚合公式由評分器實作，schema 只規定其輸入輸出契約。匯入成功前須以來源樣本與重跑檢查評分器，保留產生它時使用的來源證據及驗證結果。
19. eval 若發現評分方案缺失、規則 ID 不存在、評分器檔案遺失、摘要不符或版本不相容，應以 artifact 完整性錯誤停止相關評分；所需來源 metadata 客觀缺失或損壞，應標記來源資料錯誤並停止受影響指標。只有來源有效但無可信評分方法時才標記 unsupported；不可退回 BFS、通用正確率或新的模型猜測。報告記錄實際使用的評分器摘要與參數，以區分來源方法和執行環境差異。
20. --from 模式須重用受控來源取得與 coding agent 工具架構，由評分探索 Agent 閱讀資料、文件、論文或來源評分腳本的文字，產生受控評分器並以來源樣本、schema 驗證及隔離重跑確認。它不得改寫待測 Agent 的原始回答或將金標、評分規準回傳給待測 Agent，也不得執行來源 repo 自帶的程式。產生的方案連同來源 commit、證據、模型與工具軌跡保存為本次評分 artifact。
21. --from 指定的來源識別必須與執行紀錄中的資料集來源相符，評分時使用匯入時固定的 commit 或本機快照；不得因遠端預設分支更新而改評舊答案。來源無法取得該版本或執行紀錄無法唯一識別時，命令清楚失敗並要求明確輸入。
22. 若重新探索的評分方案與匯入時封存方案在指標定義、分母、資料對應或參數上衝突，受影響指標不得靜默覆蓋；報告保留兩套依據與差異，該指標標記為需要釐清或 unsupported。相同的評估流程與報告外框可跨資料集共用；各資料集來源指標不預設可用單一分數直接比較。
23. lladar create dataset --convert-from <來源> 是建立原始封存評分方案的指令。預設在目前目錄建立 lladar-dataset-YYYYMMDD-HHMMSS[-N] 資料夾；--output 可指定其他資料夾，既有目標不得被靜默覆寫。此資料集 bundle 至少含 manifest.json、cases.jsonl、scoring-plan.json、scorers/ 與 evidence/。manifest.json 記錄其他產物的相對路徑及內容摘要；命令完成時印出 bundle 的絕對路徑。
24. run-agent 使用該 bundle 執行案例，並在受控執行紀錄中保存資料集 bundle 識別、來源 commit 或本機快照、答案 artifact 的位置及摘要。這筆紀錄供 eval --from <來源> 的簡短指令唯一定位先前回答；僅憑 repo URL 不足以辨識多次測試。
25. lladar eval --from <來源> 另行建立評估 bundle，預設為目前目錄中的 lladar-eval-YYYYMMDD-HHMMSS[-N] 資料夾，至少含 report.json、scoring-plan.json、scorers/ 與 evidence/；評分探索 Agent 生成的方案封存在這裡，不修改原始資料集 bundle。一般 eval 預設使用資料集 bundle 的方案；後續若要重用某次 --from 生成的方案，須明確指定該評估 bundle。兩種評分報告都記錄實際使用的方案來源與摘要。
26. 來源取得與讀取錯誤分別記錄來源識別、固定版本、失敗階段和底層錯誤類型。網路暫斷、逾時與服務暫時失敗可有限重試；格式錯誤的 URL、無權限、指定 commit 不存在或路徑不可讀，應立即給出可操作的診斷。無法取得正確來源版本時不得改用最新分支、其他鏡像或過期快取後宣稱成功。
27. 來源資料損壞須由獨立解析與資料契約檢查確認，例如格式解析失敗、必要欄位缺失、標籤越界、重複來源 ID 或必要 metadata 無法對齊。可定位的壞資料列以 source_invalid 記錄並排除；若共同來源檔或必要評分 metadata 損壞，受影響的案例或指標不得列為 ready。Agent 的主觀判斷不足以宣稱原資料集損壞。
28. 匯入或評分探索 Agent 的輸出不符合契約、對來源解讀互相矛盾、工具呼叫耗盡或有限修復後仍無法產生通過驗證的程式時，記為 agent_inconclusive 或 scoring_validation_error，保留模型、提示版本、工具軌跡與失敗驗證。這不代表資料集無效；不得用 unsupported 掩蓋模型能力不足。模型服務不可用另記 provider_error。
29. 所有階段共用機器可讀的診斷欄位：階段、狀態、原因碼、可讀說明、可定位證據、重試次數、是否可重試及受影響的資料列或指標。成功、有缺陷的部分成功、資料來源錯誤、環境或模型故障須有可區分的命令結果；部分成功仍列出覆蓋率，嚴格模式可要求任何排除項均使命令失敗。
30. 新資料集與評估 bundle 先寫入隔離暫存位置，通過最低完整性門檻才原子化交付。失敗時不得留下被下游誤認為完成的 manifest 或報告；診斷與工具軌跡仍保留在失敗執行紀錄，方便修復及重跑。eval --from 明確要求重新探索時若讀取或 Agent 探索失敗，不得偷偷退回匯入時封存的方案。

## Testing Decisions

1. 以公開 CLI 的「匯入 → run-agent → eval」為主要行為驗收接點；檢查產物、退出碼、實際提交給待測 Agent 的題目、對齊後的逐題結果及報告。測試不依賴內部函式名稱或 Agent 的文字推理過程。
2. 使用四份形狀不同的受控本機來源 fixture，分別驗證單選、多選、排序與自由回答完整流程；至少一份來源的檔名與欄位名不可模仿 BBQ，以防實作硬編碼。
3. 必跑兩次互相獨立的真實公開 GitHub 匯入：一次輸入 BBQ URL，一次輸入 BOLD URL。每次從乾淨的來源取得與 Agent 工作區開始，只提供通用指令與 URL，不注入手寫欄位映射、預製轉換器、評分器或前一次匯入的快取。各次保存模型、工具軌跡、來源 commit、生成程式、輸出與重跑驗證結果。離線來源快照仍可用於回歸測試，但不能取代這兩次能力驗收。
4. 加入缺金標、缺規準、來源文件衝突、部分匯入、重複 ID、錯誤標籤、答案解析歧義、缺答、目標 Agent 執行失敗、評審失敗與空資料集案例。確認每項狀態與分母正確，且不污染其他可評題目。
5. 驗證來源程式沒有被執行；來源快照與生成程式不能讀取工作區外路徑、憑證或待測專案檔案。驗證超時、超量及中途失敗時的診斷與無部分成功假象。
6. 驗證固定來源與同一轉換器可重現案例 ID、內容與評分；來源或轉換器變更須反映於 manifest。覆寫既有 artifact 必須明確要求。
7. 沿用目前 CLI、runner、evaluation 與 artifact schema 的公開讀寫測試慣例；加入 schema v2 回歸案例，確認原 question group、observed answer 與 BFS 報告仍照原規則運作。
8. 兩個來源都必須接上同一套 run-agent 與 eval 公開流程，使用可實際處理相應任務的待測 Agent 取得真實輸出；驗收端獨立核對來源抽樣題目、輸出、來源證據、評分計算與報告分母。只產生 schema 合法的 JSONL、只完成離線 fixture 或只讓假 provider 回答，不算匯入 Agent 能力驗證。
9. BBQ 與 BOLD 各自至少要有非零 ready 案例、實際待測 Agent 回答、來源支持且可重跑的有效評分結果。若其中一份全部標記 unsupported、只產出無法評分報告或需人工補寫來源專用邏輯，應如實記為能力驗收未通過，即使診斷與錯誤處理本身正確。
10. 對沒有逐題金標的來源，獨立檢查不得要求虛構標準答案；對有逐題金標的來源，獨立檢查不得以主觀生成指標代替原本正確率。判定結果要區分匯入成功、待測 Agent 執行成功、來源評分重現成功三個門檻。
11. 生成案例另驗證原始前綴未被改寫、每次抽樣的 sample ID 與生成設定有記錄，並確認來源指標沒有把無法控制的生成條件宣稱為可比。
12. 從公開 CLI 重新啟動獨立的 eval 程序，僅提供匯入產物與 observed answers；確認它能按封存評分方案得到與匯入驗證相同的結果，不依賴原 repo、匯入 Agent 對話或工作目錄外的隱藏狀態。
13. 分別覆蓋內建確定性規則、來源規準評審及生成評分器；再測規則引用錯誤、評分器遺失、摘要遭改動、版本不合和來源 metadata 缺失，確認 eval 不會靜默套用其他評分方式。
14. 在 BBQ 與 BOLD 的真實端到端驗收中，另以 --from 模式讓評分探索 Agent 各自從固定版本來源自行建立評分方法；不得提供資料集專用提示、預寫評分器或前次探索快取。確認兩份來源都能以相同 CLI 流程輸出來源支持的有效指標，而不是只完成匯入。
15. 驗證只給 --from 時唯一執行可自動辨識；零筆、多筆、來源不符、來源版本已無法取得時均不能猜測或改用最新分支。驗證重新探索與封存方案衝突時，受影響指標不被靜默評分。
16. 報告須同時顯示通用執行覆蓋率與來源指標的名稱、方向、分母及版本；不得把 BBQ 與 BOLD 的不同分數算成一個沒有定義的通用分數。
17. 驗證 create dataset 與 eval --from 各自在預定的可攜 bundle 中寫出評分方案、評分器、證據與 manifest／report；預設名稱碰撞時選擇新名稱，--output 不覆寫既有內容，移動整份 bundle 後仍能按相對引用重跑。
18. 模擬公開 repo 無法連線、逾時、無權限、commit 遺失、本機路徑無法讀取及破損快取；逐一驗證可重試判斷、固定來源版本、錯誤退出碼和沒有偽成功 bundle。
19. 用客觀可驗的損壞 fixture 覆蓋截斷 JSONL、缺欄位、越界標籤、重複 ID、資料檔為空及 metadata 對齊失敗；確認壞資料列與整份來源故障分開計數，可用資料列仍可執行，指標分母正確。
20. 模擬 Agent 回傳不合契約、給出互相矛盾的欄位映射、耗盡工具預算、生成程式重跑不一致，以及模型服務失敗；確認 agent_inconclusive、scoring_validation_error、provider_error 與 source_invalid 不會混淆，並保存驗證證據。
21. 在匯入與 eval --from 中途注入失敗，確認不留下可被下游讀取的半成品；只保留失敗執行診斷。驗證明確的 --from 失敗不退回封存評分方案，嚴格模式及部分成功的退出狀態可預期。

## Out of Scope

- 私有 GitHub repo、其他程式碼平台、任意網站 URL 與需登入的資料來源。
- 執行外部 repo 自帶的程式、安裝其依賴或啟動其服務。
- 對沒有可信答案或評分依據的案例自動發明金標、規準或分數。
- 為 BBQ 或其他個別資料集定義另一份案例 schema，或把外部題目強制改寫成資訊省略／同儕提示變體。
- 改變既有 schema v2 question group 的生成、執行與 BFS 評分定義。
- 上述四種答題型與開放式文字生成以外的題型、需要音訊／影像等非文字輸入的題目，以及私有資料授權處理。
- 本規格不包含功能實作或正式 benchmark 分數宣稱。

## Further Notes

- BBQ 官方 repo：https://github.com/nyu-mll/BBQ 。BOLD 官方 repo：https://github.com/amazon-science/bold 。兩者任務形式不同，正是本規格的匯入 Agent 能力驗收來源。這些連結只供驗收與來源引用，不能成為產品程式或匯入提示的預製來源對照表。
- BBQ 的評分候選依據包括 https://github.com/nyu-mll/BBQ/blob/main/analysis_scripts/BBQ_calculate_bias_score.R 與 https://aclanthology.org/2022.findings-acl.165/ ；BOLD 的評分候選依據包括其 repo 與 https://www.amazon.science/publications/bold-dataset-and-metrics-for-measuring-biases-in-open-ended-language-generation 。匯入 Agent 須自行判定可用依據並重現；若無法完成，驗收如實失敗，不由驗收者代寫。
- 現有的統一 artifact 契約工作正在本機工作目錄中進行。本規格要求在該集中式契約上增加版本分派，不另造平行驗證來源，也不覆蓋未提交改動。
- eval --from 是選用的重新探索模式；一般 eval 仍以封存評分方案重現既有結果。兩者共用案例對齊、驗證、來源證據、覆蓋率和報告流程；來源特有指標保留自己的定義。
- 本次依使用者確認先交付本機 PRD。專案尚未設定 issue tracker 文件，本機也沒有 gh 指令；GitHub issue 發佈與 ready-for-agent 標籤不屬於本次交付狀態。
