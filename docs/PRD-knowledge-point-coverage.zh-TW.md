- 狀態：第一版已依 TDD 完成實作、回歸與臺南單份來源驗證；驗證範圍及限制見第 14 節。

## 2. 問題與目前觀察

目前直接問答流程可在 `submit_question` 時，依該題的 `rationale` 與來源引用建立知識點。這些知識點提供題目來源紀錄，但盤點範圍會跟著已生成題目增加。

2026-11-13 檢視 `LLaDAR-Tainan/runs/test-dataset-20261113-100545.jsonl.generation.json`，可見 10 個問答候選、10 個接受的知識點與 10 筆輸出。這組數字無法證明來源只有 10 個可測試知識點。

目前生成紀錄已保存來源、引用、知識點、問答與題目對應，可作為本案的整合基礎。現有結構與引用驗證，也需要搭配新增的語意審查，才能判斷題目實際測試哪些知識點。

本案要處理的問題如下。

1. 題目與知識點同時產生，缺少可獨立核對的覆蓋分母。
2. 重要事實可能只在答案或引用中附帶出現，卻被當成已覆蓋。
3. 難以自然出題的知識點若被自行排除，會提高表面覆蓋率。
4. 題數、已盤點數、已覆蓋數、來源讀取範圍容易混用。
5. 使用者缺少逐項查詢未出題原因、對應成立理由與覆核結果的資料。
6. 大型文件需要有限上下文的盤點方式，並須處理字元切分造成的跨段語意、條件與證據中斷。

目前來源由程式讀入本機記憶體，模型透過 `read_source` 分頁取得文本，每次最多約 12,000 個字元，並依模型設定縮小。分頁依字元位置截斷，以 `next_start` 接續。內建方法對大型來源另有分批安排，自訂 Skill 目前可在同一個 Agent 任務中分頁讀取整個來源範圍。這些機制提供分頁與批次基礎，本案進一步定義段落邊界、未完內容接續、累積上下文與逐批保存的要求。

## 3. 目標與第一版交付範圍

本案提供一份先於問答生成完成的知識點清單，同時顯示全部與可出題知識點的題目覆蓋率。每個數字都能回查到清單、對應題目與審查紀錄。

第一版交付下列能力。

- 從指定來源逐段盤點，保存固定 ID、可驗證陳述、原文位置與證據。
- 支援超過單次模型上下文的大型來源，分批保存完整知識點，接續跨批次內容，並限制每次請求的輸入與輸出量。
- 合併重複事實，保留多處引用與合併紀錄。
- 在盤點完成並保存版本後，生成問答及多對多覆蓋對應。
- 審查覆蓋對應與無法出題的申請，保存結論及具體理由。
- 從原文開始獨立覆核，修正漏盤點、錯誤拆分、漏出題及不成立的對應。
- 在題數與工作預算內補題，保存剩餘缺口及停止原因。
- 由程式計數、檢查資料一致性，集中保存雙指標與明細，由 `lladar report` 按需呈現。

第一版以「題目覆蓋」為指標範圍。目標 Agent 的執行覆蓋與逐知識點回答通過率列為後續需求，屆時須另行定義執行完成與評分規則。

`--from-github` 等其他來源入口的啟用範圍，列於第 13 節確認。共用資料中若保存本案定義的覆蓋率，須遵守相同分母與對應規則。

## 4. 術語與盤點規則

| 名稱 | 定義 |
| --- | --- |
| 來源範圍 | 本次指定來源的版本、文件清單與事實盤點規則。任何範圍限制須在生成題目前記錄 |
| 知識點 | 來源支持、可單獨判定回答是否正確的事實或命題，包含必要的主體、關係、條件與限定 |
| 盤點清單 | 依來源建立的知識點集合，包含尚未生成問題及可能無法出題的項目 |
| 可出題 | 在本次 Skill、提問者視角、題型與可用情境下，能形成自然且由來源支持的問題 |
| 覆蓋對應 | 一題實際測試某知識點的關係，須經審查接受 |
| 排除 | 知識點仍屬盤點清單，但經審查確認在本次條件下無法出題，從可出題分母扣除 |
| 獨立覆核 | 在與題目生成分開的審查工作中，先從原文檢查事實，再比對清單及題目 |

### 4.1 粒度

- 同一段可以包含多個知識點，同一知識點也可以由多段共同支持。
- 同一主體的不同事件、年代、用途或身分，若能分別驗證，應分別盤點。
- 條件、例外與否定若會改變命題真值，須與所限定的事實一起保存。拆分後的陳述仍須完整。
- 避免把整篇文章當成一點，也避免把缺少語意的單字、日期或名稱拆成獨立點。
- 例如「建築前身為臺南警察署，1998 年指定為市定古蹟」，可盤點為前身用途與古蹟指定事件兩點。指定事件須完整保留年代與古蹟層級。

### 4.2 去重與來源限制

- 摘要與正文重述同一事實時合併，所有有效證據均可保留。
- 陳述相似但主體、時期、條件或事件不同時，保留各自知識點。
- 來源互相矛盾、指涉不清或不足以確定命題時，保存待釐清項目及來源問題，交由審查處理。
- 每個來源段落須有盤點處理紀錄，可指向知識點，或記錄重複內容、標題、缺乏可驗證事實等原因。
- 文件讀取失敗或段落尚未處理時，盤點標記為未完成。這些來源問題須出現在摘要中。
- 去重與語意拆分由模型辨識及審查，程式檢查 ID、證據位置、引用與紀錄一致性。

### 4.3 Skill 的盤點原則與限制

- 開始盤點前，從選定 Skill 確定知識點粒度、事實範圍、條件與例外的保留方式、去重原則及來源證據要求，保存本次有效規則與 Skill 版本。
- Skill 未定義盤點細節時，採本文件的通用盤點規則。新增盤點契約須在內建方法與自訂 Skill 指引中明確說明。
- 提問者視角、問句風格與題型要求用於後續生成及可出題判定。盤點先保留來源支持且屬本次事實範圍的知識點，再記錄難以出題的判定與原因。
- 每批使用相同版本的盤點規則，規則變動須依版本契約重新處理受影響項目。

## 5. 覆蓋成立條件

一筆覆蓋對應須同時符合以下條件。

1. 問句在指定情境下，確實要求回答該知識點。
2. 預期答案正確表達該知識點，且有原文證據支持。
3. 既定評分要求會檢查該事實是否回答正確，缺失或錯誤會影響本題判定。
4. 覆蓋審查已接受此對應，且該題存在於本次最終輸出的資料集。

例如「這棟以前是做什麼的？」可覆蓋建築前身用途。答案或引用順帶提到「1998 年指定為市定古蹟」時，該指定事件仍須另行建立成立的題目對應。

- 允許一題對應多點、同一點對應多題。
- 一題涵蓋多點時，每個對應分別審查。問句仍須符合 Skill 的自然提問與主題集中要求。
- 選擇或排序題中，知識點僅出現在選項文字，不能自動取得覆蓋資格。
- 對圖譜、受控變體或其他題型，同樣依實際作答要求審查，並遵守既有配對及題型契約。
- 被去重、未接受、被題數上限排除或未正式輸出的候選題，均不計入本次題目覆蓋。
- 覆蓋對應被撤回或題目修改後，須重新判斷受影響關係，再計算結果。

## 6. 可出題判定與排除審查

可出題判定須保存本次提問者視角、可見情境、題型與 Skill 版本。例如臺南專案的普通大學生現場提問，會影響哪些問題可自然提出。

每個知識點至少分別保存「可出題判定」「排除審查」「覆蓋狀態」，避免將生成失敗混成無法出題。

| 狀態面向 | 必須能表達的情況 |
| --- | --- |
| 可出題判定 | 待判定、可出題、建議排除 |
| 排除審查 | 未申請、待審、接受、駁回 |
| 覆蓋狀態 | 待補題、對應待審、已覆蓋 |

- 排除申請須包含具體理由、影響的條件與證據。審查須確認是否仍有符合規則的自然問法。
- 排除理由可包含來源不足以支持所需答案、無法在可用情境中辨識指涉對象、提問必須預先知道答案等。
- 題數已滿、模型出題失敗、時間或預算不足、尚未嘗試，均記為缺口或停止原因。
- 待審與被駁回的排除申請，仍留在可出題分母。
- `eligible` 表示能自然出題，尚無對應問題時以空的題目對應表示待補題。`unresolved` 僅用於來源或情境不足，導致可出題性尚無法判定的項目。兩者分別計數。
- 接受排除的知識點保留於全部知識點分母與逐項明細。
- 若已有通過審查的有效題目覆蓋某點，該點的排除結論須重新審查。程式須拒絕同一版結果同時將它計為已覆蓋及已排除。
- 審查可以由另一個模型工作完成，第一版不要求每一項都由人類批准。須保存審查角色、結果、依據與版本。

## 7. 指標定義

所有集合以同一份來源快照、最終盤點版本、測試條件與最終輸出資料集為準。

- `K`：本版本盤點的有效、去重知識點集合。
- `E`：`K` 中經審查接受排除的集合。
- `A = K - E`：可出題分母集合，包含待判定與排除待審項目。
- `C`：`A` 中至少有一筆成立且經審查接受的最終題目對應之知識點集合。

| 指標 | 計算 |
| --- | --- |
| 全部知識點題目覆蓋率 | 已覆蓋知識點數 ÷ 全部盤點知識點數，即 `C` 的數量 ÷ `K` 的數量 |
| 可出題知識點題目覆蓋率 | 已覆蓋知識點數 ÷ 可出題分母數，即 `C` 的數量 ÷ `A` 的數量 |
| 無法出題數 | `E` 的數量 |
| 待補問答知識點數 | `A - C` 的數量，另列其中待判定、對應待審及生成失敗數 |
| 最終題數 | 最終輸出的有效題目數，獨立於知識點數 |

範例：盤點 20 點，2 點經審查接受排除，其他 18 點中有 16 點已覆蓋。

- 全部知識點題目覆蓋率為 `16 / 20 = 80%`。
- 可出題知識點題目覆蓋率為 `16 / 18 = 88.9%`。
- 無法出題 2 點，待補問答 2 點。

計算與顯示規則如下。

- 程式由集合與接受的對應計數，同一知識點只計一次。
- 保存整數分子、分母及計算版本，顯示比例時最多取小數一位。
- 分母為零時顯示「不適用」及原因。
- 比例四捨五入成 100% 時，仍以整數計數判斷是否完整覆蓋，保留缺口數量。
- 盤點或獨立覆核未完成時，可以顯示「暫定」比例及未完成範圍，不能標示為完成覆核的最終結果。
- 舊資料只有隨題產生的知識點時，顯示「尚無獨立盤點，無法計算」。
- 完成報告須說明「100% 代表本版本已盤點知識點全部有成立的題目對應」，並顯示來源覆核狀態。

## 8. 工作流程、版本與補題

1. **記錄範圍及來源快照。** 保存來源清單、內容雜湊、Skill、題型與提問情境。
2. **獨立盤點。** 依 Skill 與有效盤點規則分批讀取來源，逐批辨識完整事實、去重並保存證據，將未完內容接續處理。此工作先不生成問題，題數上限不得截斷盤點。
3. **整理並保存盤點版本。** 主程式安排獨立的清單整理工作，查核語意重複、複合事實與粒度，完成合併或拆分後，記錄已處理範圍、待釐清項目、ID 對照及清單版本。
4. **生成問答。** 依清單與本次規則產生自然問題，提出覆蓋對應及必要的排除申請。
5. **審查對應與排除。** 保存每筆結論與簡短可追查的依據。
6. **獨立覆核。** 在與生成工作分開的上下文中，先依原文及盤點規則提出漏盤點或錯誤拆分項目，再執行清單整理覆核，處理新舊知識點的同義重複及粒度，之後審查題目對應與排除原因。
7. **修正與補題。** 新發現的知識點納入新版清單。受影響的對應重新審查，在剩餘題數與工作預算內補題。
8. **計算及發布。** 依最終實際輸出的題目計數，將清單、覆蓋明細與統計集中寫入既有生成紀錄，與資料集綁定同一版本。
9. **按需產生報告。** 使用者執行 `lladar report` 時，讀取已保存的生成紀錄，產生覆蓋摘要與需要處理的明細。

### 8.1 獨立性與版本

- 第一次盤點的輸入以來源與盤點規則為基礎，避免由已生成題目決定清單範圍。
- 覆核須保存獨立的工作紀錄。使用不同模型是可選方式，第一版可由同一模型於分開的工作上下文執行。
- 知識點 ID 在同一盤點版本及續跑期間固定。合併、拆分、撤銷與修正須保存前後對照，舊紀錄仍可追查。
- 每份比例明確綁定盤點版本。題目生成或排除申請不得直接改小全部知識點分母。
- 來源快照或測試條件變動時，建立新版本，重新審查受影響的判定與對應。

### 8.2 題數與停止條件

- `--count` 沿用現有最終題數上限語意。須分別列出題數與已覆蓋知識點數。
- 達到題數上限時，列出剩餘缺口與 `count_limit` 原因。
- 題型要求的完整配對繼續適用，配對未輸出時以實際發布結果計數。
- 未指定正數題數上限時，仍受既有工作預算約束。補題須有明確的輪次或預算上限與無進展停止條件，具體預設值見第 13 節。
- 盤點、審查或補題失敗時，保存可續跑狀態與尚未完成項目。比例以當時可證明的範圍呈現。
- 達到題數目標、完成工作或完成覆核，均須與「全部知識點已覆蓋」分開記錄。

### 8.3 分段盤點與跨段接續

盤點採「讀取一批、提交完整知識點、保存進度、接續下一批」的流程。全部指定來源處理完成後，才固定完整清單版本並進入問答生成。

1. **依語意邊界取段。** 優先保留完整段落、條列項目與相關標題。遇到超長段落時，進一步沿句子邊界分段，並保留接續所需原文。
2. **提交完整內容。** 本批已能完整判斷的事實可立即接受並保存。知識點保留原文中的主體、數值、單位、條件、例外與否定。
3. **暫存未完內容。** 被切斷的句子、尚待後文限定的命題或未釐清的指涉，記錄為待接續項目，保存原文範圍及待釐清原因。完整的末段可正常提交。
4. **帶入必要前文。** 下一批帶入待接續原文、相關章節標題、主體資訊與有限前文。可使用前後重疊區域協助理解，再依新取得的原文判斷完整知識點。
5. **跨批核對。** 核對重疊處與相鄰批次的重複事實、條件及例外。較遠段落若補充或修正先前知識點，讀回相關原文與已存知識點後修訂，保留版本對照。
6. **記錄進度。** 保存本批處理結果、下一個讀取位置與待接續項目。重疊讀取後仍須推進尚未處理的來源範圍。

例如來源切分在下列位置。

```text
第一批末尾
1998 年，該建築被指定為

下一批開頭
市定古蹟，後續……
```

第一批保存該段為待接續原文，下一批取得完整陳述後，再建立包含指定年代及古蹟層級的知識點。證據須能回到原來源的實際位置，並可由多筆原文引用共同支持。

- 跨段重複事實沿用去重規則，合併後保留有效證據，同一點在分母計一次。
- 原文引用及位置作為證據。帶入的主體資訊或摘要若經模型整理，須保留可回讀的來源關聯。
- 文件末尾仍未解決的項目，轉為待釐清問題並記錄原因。盤點完成狀態須反映尚未解決的範圍。
- 一般問答生成與最終原文覆核均須能讀回跨段證據，查核未完成接續及受到遠處條件影響的知識點。

### 8.4 有限上下文、輸出與恢復

- 每批大小依模型可用 token 預算決定，預留系統指引、Skill、工具結構、必要前文、相關已存知識點及本批輸出空間。字元上限可作輔助限制。
- 每次請求只帶入本批來源與接續所需內容。已完成批次的完整原文、全部工具歷史與完整知識點清單，由持久化資料提供按需讀取。
- 跨段或跨文件語意去重時，分批找出可能重複的相關知識點，再讀取對照所需內容；全域核對同樣受每次上下文預算限制。
- 隨清單增長，使用有界的批次或工作上下文，避免每次重新攜帶完整累積清單。盤點、去重、生成及覆核均遵守此要求。
- 每批知識點可分次提交，並保存接受結果。輸出遭截斷或尚有候選待提交時，須補完或縮小工作批次，再確認完成狀態。
- 完成接續與提交後，才將對應來源範圍標記為已完成盤點。來源已被工具讀取與事實已完成盤點須分別保存。
- 接續內容過長、預算耗盡或讀取位置持續無進展時，保存問題範圍及停止原因，支援續跑。
- 逐批結果沿用既有工作階段保存，包含來源快照、有效規則、讀取及處理位置、已接受知識點、待接續內容與修訂紀錄。重試沿用已接受結果，防止重複建立知識點或跳過來源。
- 最終盤點與覆核結果仍集中於 `.generation.json`，供 `lladar report` 讀取。

### 8.5 清單整理的完成與恢復

- 主程式在初次盤點及原文覆核後安排 `inventory_reconciliation`，逐批查核清單粒度與語意重複。
- 開始前，主程式先合併去除空白與標點後完全相同的陳述，不呼叫模型。
- 每批請求直接附上本批知識點及其證據、其他知識點的精簡清單（`inventory_index`，超過預算時為 null），
  以及主程式依字元二元組相似度找出的候選重複組（`possible_duplicates`），模型不必逐頁或逐點讀取。
- 必要時仍可依關鍵詞分頁查找（每頁最多 50 筆）或讀回完整陳述及證據，再合併同義事實或拆分可獨立測試的複合事實。
- 合併保留有效證據與修訂歷史，拆分保留舊 ID 到新 ID 的替代關係，舊 ID 仍可查詢其接續 ID。
- 整理工作須提交完成確認及尚未解決的項目。接受的完成紀錄與修改即時保存，續跑沿用已完成批次。
- 盤點分次提交時，以 `complete=False` 保存部分結果，處理完整頁後以 `complete=True` 確認。缺少完成確認的頁面仍列為未完成。

### 8.6 補題與覆蓋審查的請求範圍

- 每輪補題帶入全部缺題知識點（`coverage_targets`），不再只取前 20 個。每個目標附陳述、主題與原文引用，
  引用落在既有讀取範圍內時附 `read_id`，模型可直接引用，不必逐點讀取知識點或重讀原文。
- 目標依第一筆引用位置分配給所在的生成批次；沒有目標的批次不呼叫模型。超過單批請求預算的目標列在
  `more_target_ids`，留待按需讀取或下一輪。
- 生成可用 `submit_qa_batch` 一次提交多題，逐筆接受或拒絕。
- 補題嘗試失敗且沒有任何新提交時，即使沿用前幾輪結果可通過驗證，也不視為完成，於預算內重試。
  非供應商錯誤保存截斷並遮蔽機密的錯誤訊息。
- 覆蓋審查保存每點的確定結論。知識點內容未變時，已覆蓋且所對應題目未變的點及已排除的點直接沿用，
  只重新審查缺題、待釐清、內容或對應題目有變動的點。新增題目若同時覆蓋已沿用的點，該點的題目對應可能不列出新題。
- 審查請求附上主程式依引文位置重疊配對的候選題目（`candidate_question_ids`），候選題目優先列入 `questions`；
  全部題目的單行索引（`question_index`）在預算內一併附上。模型不必逐頁翻閱題目。

## 9. 保存資料與產物

生成階段沿用資料集主檔及既有 `<dataset>.generation.json`，本案的盤點、覆蓋與審查資料集中於這份生成紀錄。閱讀用報告交由 `lladar report` 按需產生。

| 產物 | 用途與產生時機 |
| --- | --- |
| 既有資料集 JSONL | 生成時交付題目與預期答案，供下游測試 |
| 既有 `<dataset>.generation.json` | 生成時集中保存來源、獨立盤點、題目對應、排除理由、審查與覆核、缺口、版本及程式計算統計 |
| `lladar report` 的 Markdown 輸出 | 使用者執行報告命令時，從生成紀錄產生覆蓋摘要及明細，沿用報告輸出路徑與覆寫規則 |

原草案拆分的 `.knowledge.json`、`.coverage.json` 與生成時自動產生的 `.coverage.md`，統一併入上述設計。這些新增檔名從本案交付清單移除。

### 9.1 集中保存原則

- 擴充現有生成紀錄的來源、知識點、問答、資料列對應與統計結構，新增必要的盤點版本及審查內容。
- 共用同一組來源、引用與題目 ID，跨區塊以 ID 關聯，減少重複保存原文、題目與判斷理由。
- 以一份明確標記版本的最終結果為計數依據，版本變更保留必要的修訂對照。
- 續跑沿用既有工作階段管理，其內部狀態由程式管理。使用者查看結果以生成紀錄與報告為入口。
- 正式 schema 於開發設計時制定，須能辨識舊版資料並避免把隨題建立的知識點當成獨立盤點。

### 9.2 最低資料要求

- 知識點保存 ID、完整陳述、主題、來源 ID、原文引用及可定位範圍。
- 盤點保存有效規則、已完成處理範圍、未解決的跨段項目與相關來源位置。工作階段另保存逐批恢復所需位置及接續原文。
- 題目識別使用可持久化的 ID，並綁定最終記錄內容指紋。資料列位置可用於閱讀，另保留排序與內容變動的辨識依據。
- 覆蓋對應保存知識點 ID、題目 ID、審查狀態與成立或不成立理由。
- 排除紀錄保存適用的測試條件、申請理由、審查結果及審查版本。
- 覆核紀錄保存來源範圍、發現的問題、處理結果與仍未解決的項目。
- 統計保存整數計數、盤點版本、資料集指紋、計算規則版本及結果是否暫定。
- 模型提供簡短判斷依據與證據，不要求保存內部思考過程。

程式對工具提交及 Python 產生的結果套用同一份最終一致性驗證，檢查未知 ID、失效引用、重複計數、排除與覆蓋矛盾，以及生成紀錄與最終資料集版本不一致等情況。

發布與重試須沿用既有覆寫及工作階段契約。資料集與生成紀錄須能驗證版本一致，避免中斷或重試後把舊覆蓋結果配上新題目。

## 10. 使用者呈現

沿用現有命令操作，下列指令執行本案流程。

```powershell
lladar create test-dataset --knowledge .\Knowledge --skill .\test-dataset-skill --output .\runs --lang zh-TW
```

### 10.1 生成階段的精簡摘要

進度顯示目前正在盤點、生成、審查、覆核或補題。完成時顯示以下摘要。

- 最終題數，以及全部與可出題知識點的題目覆蓋率，附分子與分母。
- 待補題、排除、待審數量，以及覆核或生成未完成的提示。
- 資料集與生成紀錄位置，以及可直接複製的 `lladar report` 指令。

逐點對應與原因集中保存，使用者需要閱讀時再產生報告。

### 10.2 由 `lladar report` 產生覆蓋報告

`report` 接受生成紀錄作為輸入，沿用同一個位置引數及 `--output` 等既有操作。

```powershell
lladar report .\runs\test-dataset-20261113-100545.jsonl.generation.json --output .\runs\report.md --lang zh-TW
```

- 命令依檔案內容及 schema 辨識生成紀錄與既有評估結果，分別呈現適用的報告。
- 生成紀錄已包含本次來源、盤點、題目對應與審查資料，生成完成後即可產生題目覆蓋報告。
- 覆蓋數字由程式根據保存的集合與對應重新計算，並核對版本及統計。報告生成沿用已保存的盤點與審查結論。
- 基本覆蓋報告以確定性方式呈現比例、狀態與明細。若選用模型撰寫說明，數字與狀態仍以程式計算為準。
- 預設報告先呈現雙指標與覆核狀態，再列待補題、排除、待審及來源未完成項目。已覆蓋項目以數量摘要呈現，完整對應保留於生成紀錄。
- 逐項問題明細包含知識點 ID、陳述、已有或缺少的題目對應、原因與審查狀態。例如下表中的待補題項目。

| 知識點 ID | 知識點 | 對應問題 | 覆蓋狀態 | 排除／缺口原因 | 審查狀態 |
| --- | --- | --- | --- | --- | --- |
| kp_000002 | 1998 年指定為市定古蹟 | — | 待補題 | 達到本次題數上限 | 可出題 |

- 缺少獨立盤點的舊紀錄，須呈現「尚無獨立盤點，無法計算」及可確認的既有統計。
- 紀錄不完整或統計與底層對應不一致時，呈現可追查的問題與暫定狀態，要求修復受影響資料。
- 既有評估報告若要整合覆蓋章節，須取得可驗證且與本次資料集對應的生成紀錄。跨階段關聯方式列於第 13 節確認。

`--no-verbose` 時仍顯示精簡摘要與產物位置，`--log` 保存終端呈現內容。所有新增介面文字遵守既有 `--lang` 規則，來源引用與已有題目文字依其既有資料契約保存。

來源證據集中於生成紀錄。一般 `.operation.md` 作業結果報告沿用既有允許欄位，呈現統計、狀態與產物位置。

## 11. 相容與資料沿用

- 下游 `run-agent` 與 `eval` 沿用現有主要資料格式。`report` 增加生成紀錄輸入及覆蓋呈現，既有評估結果輸入繼續適用。
- 載入舊資料時，辨識是否具備獨立盤點及審查紀錄。缺少時標示覆蓋率不可計算。
- 未來若要為舊資料補算，須先建立獨立來源盤點、審查既有題目的對應，再產生新的覆蓋版本。
- 既有可追查的來源引用、候選題與問答紀錄可作為輸入，不能直接視為已完成本案盤點或審查。
- 自訂 Skill 的提問風格與方法繼續適用。啟用覆蓋流程時，主程式與 Skill 契約須清楚說明盤點、對應與審查的交付責任。
- 本案驗收需包含內建 Skill 及臺南專案的現場自然問答 Skill，並檢查題目仍符合提問者視角。

## 12. 驗收條件

本次 TDD 已確認透過 `create_test_dataset()` 與 CLI `main()` 測試公開行為，包含發布資料、續跑及報告。模型回覆以外部模型介面的替身提供，另以真實模型及臺南來源驗收。

| 情境 | 預期結果 |
| --- | --- |
| 獨立盤點 20 點，接受排除 2 點，覆蓋 16 點 | 顯示 80%、88.9%、排除 2 點、待補 2 點 |
| 生成 10 題，清單有 20 點 | 分母維持 20，依成立對應計算覆蓋 |

| 答案或引用附帶提到另一事實 | 該事實須有成立的作答要求與審查對應才能計入 |
| 摘要與正文記載相同事實 | 合併為一點，保留多處證據 |

| 排除已接受，但同點也有接受的有效題目 | 一致性驗證阻止矛盾結果發布，要求重新審查 |

| 選項文字或圖譜引用出現某知識點 | 仍依實際作答要求審查該點的對應 |
| 原文覆核發現漏盤點 | 建立新盤點版本、加入遺漏點並更新統計 |

| 修改題目、重排資料列、合併知識點或續跑 | ID 對照、內容指紋、版本與統計可追查且一致 |
| 部分寫檔失敗後重試 | 辨識不完整結果，依既有恢復契約產生一致的產物 |
| 以工具或 Python 產生候選結果 | 最終套用相同的證據及一致性驗證 |

| Skill 定義盤點粒度與證據限制 | 各批採相同有效規則，保留規則及 Skill 版本 |
| 某事實難以符合提問者的自然問法 | 先保留於盤點清單，再依可出題與排除規則處理 |
| 來源大於模型單次上下文 | 分批完成盤點與保存，各次請求包含必要輸入及輸出預算 |
| 截斷位置落在指定事件的年代與古蹟層級之間 | 保存待接續原文，下一批建立完整命題與可定位證據 |
| 本批最後一段已完整 | 可正常提交，處理紀錄能追查其知識點 |
| 下一批使用「他」「該建築」等指涉 | 帶入相關主體及必要前文，核對原文後建立完整知識點 |
| 重疊區域再次辨識出相同事實 | 合併證據、保留知識點身分，分母計一次 |
| 遠處段落提供例外或限定 | 讀回相關知識點與原文，修訂命題並保留版本對照 |
| 知識點清單與工具歷史持續增長 | 每次模型輸入按需讀取且受預算約束 |
| 批次輸出遭截斷，或讀過來源但候選尚未提交完 | 保留進度並補完，對應範圍標示尚未完成盤點 |
| 盤點中斷後續跑 | 恢復已接受知識點、來源位置與接續內容，核對來源快照及規則版本 |
| 文件結尾仍有未釐清接續項目 | 保存原因與來源範圍，摘要與報告顯示未完成狀態 |
| 最終原文獨立覆核處理大型文件 | 同樣分批檢查，特別核對切分邊界、跨段限定及未解決項目 |
| 原文覆核以不同措辭重新提出既有事實 | 固定執行清單整理，合併語意重複並保留證據與 ID 對照 |
| 同一知識點同時描述前身用途與古蹟指定事件 | 拆為獨立知識點，再逐點審查題目是否確實測試該事實 |
| 能自然出題但本次沒有對應問題 | 判為 `eligible` 且對應為空，計入待補題 |
| 來源或情境不足，無法判定可出題性 | 判為 `unresolved`，留在分母及待審數量 |

離線驗證涵蓋分段邊界、上下文及輸出預算、接續、去重、計數、引用、狀態、版本、題數選取、相容與恢復。真實模型驗收另以臺南來源及大型文件案例檢查跨段完整性、盤點粒度、漏盤點、自然問句、對應及排除理由，保留逐項人工抽查紀錄。各類驗證結果分別記錄。

## 14. 交付與驗證順序
