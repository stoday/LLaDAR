# PRD：四階段的工具提交、局部修正與進度保存

## 狀態與文件關係

- 日期：2026-10-11。
- 狀態：使用者已於 2026-10-11 授權依 TDD 開始實作；新增測試介面確認中，功能尚未實作完成。
- 適用流程：`create test-dataset` → `run-agent` → `eval` → `report`。
- 使用者目標：Agent 透過 tool 交付內容；單筆格式問題可以修正，不拖垮整批工作；避免 Agent 自行處理作業系統路徑與檔案序列化。
- 本文件補充既有 [GitHub 生成 PRD](PRD-github-dataset-generation.zh-TW.md)、[Agent 選用生成方法 PRD](PRD-agent-selected-dataset-generation.zh-TW.md)、[題型 PRD](PRD-question-type-test-dataset.zh-TW.md) 與 [評估準則 PRD](PRD-evaluation-criteria.zh-TW.md)。未明確修改的既有契約保持有效。
- 沿用 `CONTEXT.md`：正式 question record 為 `question`、`expected_answer`、`actual_response`；執行失敗的回應為 `null`；判斷由 Agent 提供，統計由程式計算。

| --- | --- | --- |

| BBQ | 3 題，生成 2 輪 | 檔案中的題目與已提交答案依據的 fingerprint 不一致；修復後題幹仍有反斜線加單引號的跳脫痕跡，模型查驗仍批准 |

實測產物：[CBBQ 查驗報告](../.tmp/github-cbbq-acceptance-v1/dataset.generation-report.md)、[BBQ 查驗報告](../.tmp/github-bbq-acceptance-v1/dataset.generation-report.md)、[問題整理](../.tmp/github-cbbq-bbq-review.json)。這些是本機驗收檔案，未納入版本控制；未執行原 benchmark 評分。

本次要處理的根因：多次手動序列化、用內容文字作為可修改草稿的關聯鍵、錯誤回饋不足以精準修復，以及完成內容沒有一致的持久化方式。

## 目標與非目標

### 目標

1. Agent 使用少量、明確的工具提交業務內容，工具管理 ID、引用、驗證、保存與正式輸出。
2. 可修正問題影響單筆草稿；已接受的其他內容保留。
3. 中斷後可在相同輸入與契約下續作，避免重新生成、重新判斷或重跑已完成試次。
4. Windows、Linux、macOS 使用相同工具參數，不要求 Agent 撰寫 shell 指令或拼接本機路徑。
5. 成功、部分完成、單筆失敗與整體中止的證據可查驗。

### 非目標

- 不保證所有錯誤都能自動修復，也不把格式相容當成語意正確。
- 不改寫受測 Agent 的回答，不補造缺失證據或評估結果。
- 不重設題型、評分標準、原 benchmark 指標或 CLI 的既有預設行為。
- 大量資料需求先涵蓋 CSV／JSONL 的受限串流與分批處理；大型 JSON、壓縮檔及外部資料平台另行規劃。多模型審查或自動調整評分準則不在本次範圍。
- 第一輪不擴充 situation 的新互動行為；既有 situation 流程需保持相容，之後另行決定導入範圍。

## 共通工作契約

### 1. 工作 session 與穩定 ID

- 每次階段工作建立 `session_id`，保存輸入雜湊、Skill／準則版本、模型設定、工具契約版本與工作狀態；不保存憑證值。
- 工具產生草稿、試次、判斷與段落 ID。ID 不依賴可修改的題目文字、本機絕對路徑或重新排列後的列號。
- 草稿修改保留同一 ID 並增加 revision；每次修改保存可觀察的變更與驗證結果，不保存模型私密推理。
- fingerprint 用於正式內容完整性檢查與去重，不用來連結尚會修改的草稿與答案依據。
- 同一請求的重送不得產生重複項目。提交使用可重用的 request ID；相同 ID 配不同內容回傳衝突，不能默默覆寫。

### 2. 工具回傳一致的修復資訊

工具名稱與範例欄位為提案；實作前確認公開工具契約。

```json
{
  "status": "needs_revision",
  "item_id": "question_003",
  "revision": 1,
  "issues": [
    {
      "field": "source_refs",
      "code": "unknown_source",
      "message": "來源不存在，請使用來源讀取工具回傳的引用 ID",
      "repair_action": "replace_source_ref"
    }
  ]
}
```

- `accepted`：通過該次工具驗證並已保存；不代表已通過後續語意審查或正式發布。
- `needs_revision`：可修正問題，保留草稿與其他已接受內容。
- `rejected`：達到修復額度或無法符合必要條件；保存原因，不列為有效成果。
- `conflict`：版本、request ID 或修改目標不一致；回傳目前狀態供呼叫端處理。
- 回饋需指明欄位與問題；不只回傳泛用的 `InvalidCandidates` 或 Python exception 名稱。
- 超時或未知 transport 結果時，先查詢 request／item 狀態，確認是否已保存，再決定重送。

### 3. 草稿彈性與正式驗證

- 模型支援結構化 tool calling 時使用其原生機制；工具仍需驗證參數，不以模型宣稱格式正確取代驗證。
- 區分表示法問題與語意問題。JSON 空白、換行表示等由標準序列化處理；缺失來源、未知標籤定義或答案衝突不能靠格式修補通過。
- 不以全域字串替換刪除反斜線、改單引號或猜測資料欄位。合法程式碼、路徑與引文必須保留。
- 未知欄位或舊版欄位使用明確、版本化的相容規則；沒有規則時給修正回饋，不靜默丟棄可能有意義的內容。
- 每筆預設最多 3 次修正，額度與使用次數記錄於 session。重送同一已保存請求不重複消耗修正額度。
- 草稿的接受、更新與保存需為單一原子操作；不能出現題目已保存、答案依據未保存卻回傳成功。

### 4. 保存、中斷與正式發布

- 工作資料預設放在輸出位置旁的獨立工作目錄，正式產物與草稿分離。Agent 使用 ID，不需要知道目錄名稱。
- 每筆被接受的結果立即建立持久化 checkpoint；下次讀取時檢查完整性。不得宣稱已保存但只有記憶體狀態。
- 同一 session 同時只能有一個 writer，避免並行續作互相覆寫。
- 中斷後保存最後可確認的狀態；若磁碟無法寫入，清楚報告保存失敗，不承諾保留最後一筆。
- 正式發布前凍結結果、計算統計並驗證全部必要產物；完成標記最後發布。使用者既有正式檔案不得因失敗被破壞。
- 即使某些項目失敗，符合該階段必要條件的有效成果仍可發布，並清楚列出未完成項目。
- 不改變既有 exit code 契約；階段是否完成、是否部分完成、有效／失敗項目數在摘要與 sidecar 明確表示。

## 四階段需求

### A. create test-dataset

建議工具：來源讀取、`submit_question`、`revise_question`、草稿狀態查詢、`finalize_dataset`。

- 來源工具回傳可引用的 `source_ref`。程式保存固定版本、原文、資料列與欄位位置、雜湊；引用 ID 不依賴本機暫存路徑。
- 一次提交題目、預期答案、來源引用、答案依據與轉換說明。程式抽取原文證據，不要求 Agent 重抄整個資料列 JSON。
- 來源引用能指向多列或必要的欄位／標籤定義；只引用資料檔名不足以支持答案。
- 原始 QA、原始標註、衍生判準需分開。宣稱保留原始答案時，保存欄位／標籤對應的來源依據；有意修改問題或判準必須記錄。
- 正式保留原始選項的題目，由程式確認選項內容與答案對應；合法文字跳脫與模型留下的呈現瑕疵不能混為一談。
- 每題獨立修正與審查；成對題沿用既有整對保留／排除規則，不能為湊題數破壞配對。
- `--count` 仍是正式輸出的上限；不足時記錄原因，不自動無限補題。
- GitHub 正式產物仍包含 JSONL、來源快照、生成查驗報告與 generation sidecar。題目與證據 ID 放在 sidecar，維持正式 JSONL 的既有契約。
- 本機 `--knowledge`、直接 QA、選用圖譜及既有題型保持可用；先遷移直接 QA，圖譜路徑透過相同保存與正式驗證規則銜接。
- Agent 自行寫候選檔不再是內建方法的主要交付方式；既有候選檔與自訂 Skill 路徑在相容期仍經相同驗證入口匯入。

### B. run-agent

建議工具／host 行為：查詢已凍結的排程、執行單筆試次、記錄實際回應／失敗、查詢試次狀態、完成 run。

- 不要求受測 Agent 安裝 LLaDAR 工具。外部 Agent、Python callable、API 與瀏覽器由既有 adapter 呼叫，host 記錄試次。
- 一次執行有獨立 `trial_id`；排程順序與案例關係固定保存，不能靠答案文字辨識試次。
- 單筆已知執行失敗留下 `execution_error`、實際診斷與可取得的部分捕捉資料，再依既有策略繼續。
- `actual_response` 僅由實際捕捉的最終答案取得；不得由模型補造、修正或把進度訊息當成答案。
- 成功／失敗試次逐筆 checkpoint。續作不重跑已完成試次；全數執行失敗仍可交付完整失敗紀錄，但不能宣稱有效回答成功。
- 請求已送出但完成狀態未知時，記為 `completion_unknown` 的工作狀態，不自動重送受測請求。使用者明確指定重試時才建立新 attempt，保留原紀錄。
- 測試策略刻意重複的試次是不同 trial，不得被去重機制吞掉。

### C. eval

建議工具：既有 `submit_plan`／`submit_judgment` 加上穩定 ID、修正與查詢能力，再完成 evaluation。

- 評估計畫先驗證、凍結；逐筆 judgment 引用 `trial_id`、plan 版本與證據。
- 計畫格式錯誤可局部修正；凍結後不能在某題失敗時偷偷更換評分標準。更換準則需建立新 evaluation session。
- judgment 格式或範圍錯誤只修正該筆。達到額度後記錄 `judge_error`，繼續其他可評估試次；既有 `strict` 模式保持其停止語意。
- 無法由證據判斷，使用計畫允許的不確定結果；計畫沒有此結果時記錄無法有效判斷，不能自動新增分值或猜答案。
- 受測執行失敗與評分失敗分開；不能把 `execution_error` 當作模型答錯的有效判斷。
- 程式計算統計，分母與排除範圍明確；續作只處理未完成 judgment。

### D. report

建議工具：讀取凍結的 evaluation facts、提交／修正個別段落、查詢狀態、完成 report。

- Agent 撰寫 overview、findings、limitations 等敘述；正式統計表由程式產生。
- 每段引用事實或 trial／judgment ID。工具驗證引用存在並屬於本次 evaluation；模型檢查敘述是否有充分支持。
- 一段格式錯誤不要求重寫全部報告；接受的段落逐筆保存。
- 必要段落未完成時保存草稿與原因，不能發布看似完整的正式報告。有效的 evaluation JSON 保持可用。
- 下游結果缺失、執行錯誤、judge error、樣本不足與人工未審閱須如實呈現。
- Agent 文字不能覆寫統計值；敘述中的具體數字必須對得上凍結的 facts。

## 錯誤分級

| 類型 | 處理方式 |
| --- | --- |
| 工具參數或單筆內容可修正 | 回傳 `needs_revision`；保留其他成果 |
| 單筆來源或證據不足 | 要求補證據；額度用盡後拒絕／跳過並記錄 |
| 受測單筆執行失敗 | 記錄 `execution_error`；沿用執行策略 |
| 模型服務暫時不可用 | 有界重試；額度用盡保存 checkpoint 並中止受影響階段 |
| 來源、準則、Skill 或契約版本不匹配 | 拒絕續作；既有成果保留，建立新 session |
| 權限、磁碟、持久化毀損或未知程式錯誤 | 中止，不把未知錯誤吞成成功；保留可確認的診斷與 checkpoint |

## 四階段的大量資料處理

- 分開控制下載／讀取額度、保存額度、每批筆數與模型輸入額度；提高下載上限不等於將整檔送進模型。
- CSV／JSONL 串流以完整資料列為單位，保留原始 ID、邏輯列號與來源引用。CSV 欄位中的換行不能被當成多筆資料。
- Agent 根據欄位與預覽提出取樣計畫，程式執行可重現的取樣；如未完整讀取來源，不宣稱是全資料隨機取樣。
- 生成分批讀取樣本與必要標籤定義，完成一批即保存；正式發布前跨批去重、檢查配對與 count 上限。
- run-agent 逐筆執行與持久化，並行需有明確額度；長回應／對話保存完整原文，避免累積全部內容於記憶體。
- eval 逐筆或分批使用同一份凍結準則；超長單筆按評估需求分段，保存讀取範圍與必要證據。不能把默默截斷或模型摘要當成完整原文評估。
- report 由程式對全部有效結果計算統計，Agent 按需讀取案例證據並分段撰寫；樣本案例不得被當成完整資料的統計。
- 分批涵蓋全部資料與僅處理樣本必須區分。報告記錄讀取、選取、處理及正式交付範圍、停止原因、未處理內容，以及完整來源與樣本的不同雜湊範圍。
- 每批完成與 checkpoint 保存配合共通 session 契約，中斷後不重做已完成項目；讀取額度耗盡時依階段記錄部分結果或無法完成，不能隱藏缺失。

### 程式保護額度與模型容量的區別

下載／儲存、掃描與抽樣、模型輸入／輸出是不同層的額度，不能以其中一層的數值
代表全部容量。GitHub 一般文字下載每次回應 2 MiB、串流抽樣 CSV／JSONL 單檔
16 MiB、累計下載 20 MiB、最多掃描 200000 列並保留 100 列，屬於程式保護額度；
它們控制傳輸、儲存、掃描及後續生成成本，不是模型的上下文硬性上限。

模型容量依模型及服務商而定，由模型 profile 與輸入／輸出 token 額度控制。
內建來源批次另受最多 24000 字元與模型輸入額度限制；抽樣也須符合選取文字額度。
字元、UTF-8 位元組與 token 不可直接等同。提高 token 選項不改變下載或抽樣額度，
也不代表可以將整份大檔案一次送入模型。

目前下載上限是內建設定，未提供專用 CLI 調整選項。放寬額度須另外驗證資源消耗、
跨批整合與關係保留。超限應明確停止或揭露部分處理範圍；已有 checkpoint 時提供
接續方法，不宣稱任意大小皆可成功。GB／TB 級處理尚未驗收，抽樣與完整處理需分開描述。

## tqdm 進度顯示

使用者已指定分批處理時以 `tqdm` 顯示進度。由 host 根據實際工作事件更新，Agent 不計算百分比或自行繪製進度條。

### 開關與輸出

- CLI 沿用 `--verbose`／`--no-verbose`，公開 Python API 使用 `verbose=True/False`，預設顯示進度。report 若尚無相同入口，新增一致的開關。
- `verbose=True`：互動終端使用 tqdm 進度條，顯示階段名稱、已處理量、可確認的總量、耗時、速度與可估計的 ETA。
- `verbose=False`：隱藏進度條與等待心跳；既有必要摘要、錯誤與輸出路徑仍保留。
- 進度輸出至 stderr，不污染 stdout 的資料或正式 JSONL／JSON。既有題目、答案預覽與診斷訊息需透過協調的輸出方式插入，不能覆蓋或打亂進度條。
- `--log` 保存時間戳與實際進度事件，避免保存動態重繪控制字元。啟用 log 不應讓互動終端失去可用的進度顯示。
- 非互動終端、CI 或重新導向時，降級為節流的逐行進度，不持續輸出回車重繪內容。
- Windows、Linux、macOS 與窄終端均需可讀；支援 ASCII 進度條回退，不依賴特定 shell。

### 計數規則

| 工作 | 主要進度單位 | 額外資訊 |
| --- | --- | --- |
| 來源下載／讀取 | bytes 或完整資料列 | 已讀取量、額度與取樣範圍 |
| 題目生成／查驗 | 已排定工作項目或批次 | 有效題數、待修正、拒絕、跳過 |
| run-agent | 已結束 trial／排程 trial | 成功、失敗、未知完成狀態 |
| eval | 已結束評估工作／排定工作 | 有效 judgment、judge error、execution error |
| report | 已完成段落／必要段落 | 正在查驗／修正／發布 |

- 批次大小不同時，筆數主進度依各批實際已結束項目更新，批次序號可作為附加資訊；不能把不同大小的批次視為相同工作量。
- 只有總量可確認時顯示百分比。來源長度或待處理量未知時顯示已處理量與耗時，不捏造總量、百分比或 ETA；估計值需明確標示。
- `--count` 是正式題數上限，不直接當成已確定的生成工作總量。模型仍在規劃、修正或篩選時，不宣稱已完成相同數量的有效題目。
- 重試與修正顯示 attempt／revision，但不重複增加主進度；成功、跳過與最終失敗分開計數。
- 處理進度達到 100% 只代表排定工作已結束，不代表所有項目成功；完成摘要必須顯示有效、失敗與跳過數量。
- 續作從 checkpoint 的已完成數開始，並標示本次接續處理量。
- 模型等待期間沿用等待心跳／狀態，不能為了讓進度條動而增加虛構的完成數。
- 正式發布獨立顯示為最後階段；工作全部處理完但尚未發布時，不顯示整體成功。中斷或錯誤時關閉進度條並輸出明確狀態。

## CLI、公開 API 與相容性

- 既有四階段指令、輸入方式、正式檔名規則與 `--force` 的覆寫意義不變。
- 提議新增明確的 `--resume SESSION_PATH`，公開 API 對應 `resume`；session 路徑供使用者選取，不作為 Agent 的內容參數。
- 續作檢查輸入內容、Skill／準則、模型設定、工具契約與上游成果；不匹配時列出差異並停止，不混合不同條件的結果。
- `--resume` 不等於重跑或覆寫；不能與 `--force` 同時使用。已完成 session 不重複發布或呼叫模型。
- 受測請求完成狀態未知的重試方式在 run-agent 導入前另行確認；預設續作不會自行重送。
- 自訂 Skill 原有提交工具透過明確 adapter 保持相容，並顯示新契約可提供的能力；不能要求所有既有 Skill 立即重寫。
- 正式 artifact 的 sidecar 若需新版本，提供版本識別與 reader 相容；不悄悄改變既有欄位意義。
- UTF-8、原文保留與 host 路徑處理由共通 module 負責；不用 prompt 指定不同作業系統的 shell 寫檔方法。

## 導入順序

1. **第一階段：生成。** 實作來源引用、原子題目提交、穩定 ID、修正回饋、checkpoint、受限串流／分批與 tqdm 進度；先以 TWBias、CBBQ、BBQ 驗證。
2. **第二階段：評估與報告。** 沿用已驗證的共通 module，改進 plan／judgment／段落提交、分批讀取、進度與續作。
3. **第三階段：run-agent。** 補逐筆持久化、排程續作、進度與未知完成狀態處理；保留不同 adapter 的真實執行與捕捉行為。

每階段須完成自己的驗收才能擴展，不先全面替換四階段，也不讓共通 module 承擔各階段的語意判斷。

## 驗收條件

### 共通

- 單筆缺欄位、未知引用與版本衝突能收到可修正回饋；其他已接受內容不遺失。
- 同一 request 重送不重複保存；相同 ID 的內容衝突被明確拒絕。
- 提交成功後中斷並重啟，可找到相同 item ID 與 revision；已接受內容不重新呼叫模型。
- 原子保存中途失敗不留下半筆已接受內容；正式發布失敗不破壞先前正式產物。
- Windows、Linux、macOS 的離線契約／持久化測試通過；不能只在 Windows 實測後宣稱跨平台已驗證。
- 單引號、雙引號、反斜線、換行、中文與合法程式碼內容能完整保存；不得以破壞原文的清洗換取通過。
- 大於目前單檔上限的 CSV／JSONL 可在明確額度內逐列取樣／分批，保存原始列引用；測試涵蓋 CSV 欄位中的換行與串流中斷。
- 長內容評估可核對實際讀取範圍；部分讀取或取樣在結果與報告明確揭露，統計分母不混用完整資料與樣本。

### 進度驗收

- verbose 開啟時已知總量的工作顯示 tqdm；未知總量顯示累計量，沒有虛構百分比。
- verbose 關閉時沒有進度條與心跳，必要摘要與錯誤仍可見。
- 批次大小不同、重試、跳過、失敗與續作時，已處理數及有效數一致；不因重試超過總量。
- 等待、查驗與發布階段能辨識，不提前宣稱整體成功。
- 題目預覽與診斷不破壞進度條；stdout 及正式產物不含進度文字，log 不含重繪控制字元。
- 實測互動終端、非互動輸出、`--log`、Ctrl+C 與跨平台 ASCII 回退；以公開可觀察行為驗證，不只檢查是否呼叫 tqdm。

### 分階段

- 生成：QA 與答案依據原子保存；修正題目不失去引用；未知來源被拒絕；原始 QA 與衍生規則可區分；成對題與 count 契約保持有效。
- 生成實測：僅傳入 TWBias、CBBQ、BBQ 根 URL，各最多 3 題；核對逐題證據與文字完整性。若有題目被拒絕，記錄理由；不能為達到 3 題放寬必要驗證。
- eval：一筆 judgment 格式錯誤可修正；無法修正記為 judge error；計畫、分母及有效結果正確保存；strict 行為不變。
- report：只修正有問題的段落；統計由 facts 產生；未知引用不能接受；必要段落不全時只有草稿。
- run-agent：一筆失敗不遺失其他回應；已完成試次續作不重跑；未知完成狀態不自動重送；合法策略重複仍有不同 trial ID。
- 既有 CLI、Python 公開 API、自訂 Skill、題型與下游讀取回歸測試保持通過。
