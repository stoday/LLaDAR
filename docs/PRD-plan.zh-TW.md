# lladar plan：以對話建立可執行的測試計畫

> 本文件保留作為歷史背景；目前實作依據為 [plan v2 PRD](PRD-plan-v2.zh-TW.md)。

日期：2026-10-28。狀態：提案，待討論；本文件不代表功能已實作。

## 1. 問題與產品定位

LLaDAR 透過 Agent 與 Skill 提供彈性的生成、目標探索、執行、評估及報告能力，但使用者目前需要自行完成兩個困難的決策：

1. 判斷自己的測試需求是否能由現有介面與證據支持，以及最後可以得到什麼結論。
2. 把需求轉成適當的單題或多輪方法、目標入口、評估準則、檔案與命令參數。

命令合法並不代表方法適當；流程執行成功也不代表已測到原本想知道的行為。只增加參數說明或讓 Agent 猜一條命令，無法完整解決這兩個問題。

新增 `lladar plan` 作為對話式測試規劃入口。命令啟動後由 plan agent 與使用者對話，協助釐清目標、資料、方法、觀測能力與限制，再將結果轉成現有 `create`、`run-agent`、`eval`、`report` 的操作。使用者仍可直接使用既有命令。

核心承諾：使用者能在實測前理解「這次測什麼、怎麼測、缺什麼，以及結果能說到哪裡」。

## 2. 目標與非目標

### 目標

- 使用者能用自然語言開始，不必先理解 CLI 與 Skill 的完整設計。
- 只追問會影響方法、可行性或必要輸入的資訊，避免固定問卷式對話。
- 區分現有支援與目前無法測量的需求。
- 交付可閱讀計畫、必要配套檔案及依序執行的命令，並對命令與依賴做程式檢查。
- 記錄使用者明確需求、採用的假設、未解問題與驗證限制。
- 優先使用現有內建方法與 `--criteria`；現有能力不足時明確標記阻擋，不生成新的 Skill。

第一版的重點是對話式需求釐清與既有能力規劃。`lladar plan` 下達後即進入互動對話；若帶有位置參數，將它作為對話起點，而不是直接推導並執行命令。

### 第一版不包含

- 自動執行出題、受測目標呼叫、adapter 探索、評估或報告。
- 新的測試執行引擎、評分機制、外部 benchmark scorer 或目標協定。
- 保證任意自然語言測試都可實現，或保證自訂 Skill 的語意正確。
- 第一版不建立、修改或生成新的 Skill；若現有能力不足，只指出缺口並將計畫標記為 `blocked`。
- 自動安裝依賴、修改受測專案、啟動服務、操作登入或取得憑證。
- 新的通用設定框架、背景服務、多 Agent 分工或計畫執行命令。
- 跨次規劃的對話續接；保存的計畫可閱讀及手動使用，第一版不提供 plan resume。

## 3. 使用者故事

1. 第一次使用的使用者說「想測客服是否亂答退款問題」，plan 幫助區分違反規則、資訊不足與多輪承諾，並說明各自需要的資料。
2. 使用者只有聊天網站，plan 選擇網站入口並揭露後續登入與資格化需求，不要求使用者先找出 API。
3. 使用者已有題庫與回答，只想換準則分析，plan 從 `eval` 開始，不要求重新出題或重新呼叫目標。
4. 使用者想確認業務操作真的完成，plan 發現只有文字回覆，指出缺少系統狀態證據，不把「聲稱完成」改寫成「已確認完成」。
5. 進階使用者提供既有 Skill，plan 說明它作用於哪個階段，以及哪些需求超出該階段契約；plan 不修改 Skill。

## 4. 提議的 CLI

以下為第一版介面：

```powershell
lladar plan
lladar plan "我想測客服在資訊不足時會不會追問" --lang zh-TW
lladar plan --output ./runs/refund-plan --lang zh-TW
```

- 可選位置參數為初始需求；省略時由第一輪對話取得。
- `--output DIRECTORY` 指定計畫包目錄；預設使用 `runs/plan-YYYYMMDD-HHMMSS`，碰撞時加流水號。
- 沿用 `--model`、`--env-file`、`--lang`、`--log` 的既有慣例；`--model` 只設定規劃 Agent，不自動指定後續所有階段的模型。
- 第一版不增加完整的一套測試設定旗標。目標、來源、題數與方法由對話取得。
- 需要互動終端。非互動環境在模型呼叫前說明限制並停止；無人值守模式不屬於第一版。
- 明確指定的輸出目錄已存在時停止，不提供自動覆寫。中斷不留下標示為完成的計畫包。

精確的模型預設與對話資源上限沿用專案現有設定方式，在實作時固定；需要在對話開始時顯示，不以無限對話作為完成策略。

## 5. 對話流程

對話以四個工作階段為主線，依序釐清。畫面顯示目前階段，例如「1/4 準備題目」。各階段的問題、選項與建議由 plan agent 根據對話生成，每題最後保留「自己輸入回答」；不使用反覆出現的通用行為選單，也不要求使用者逐階段批准。

| 階段 | 主要問題 | 需要釐清的內容 |
| --- | --- | --- |
| 1. `create test-dataset` / `create situation` | 有沒有知識文本？還是要依想測的行為設計題目？ | 知識來源、想檢查的表現、案例數；多輪情境另需情境指示、停止條件及輪數上限 |
| 2. `run-agent` | 要測的 Agent 是專案、API，還是其他支援的入口？ | 專案路徑、API 使用指南或聊天網站入口，以及與前一步測試模式是否相容 |
| 3. `eval` | 怎樣的回答算符合要求？ | 預期答案、情境判準或 `--criteria`，並以白話描述成功與失敗的例子 |
| 4. `report` | 希望報告著重哪些結果？ | 總覽、失敗案例、判斷依據與詳細程度；目前以既有 Markdown 報告為交付格式 |

已有資料直接沿用，跳過已完成工作；只有新回答改變先前決定時才回頭確認。第一題從題目來源開始，測試目標在這個階段按需要釐清，不另開一輪通用分類。

四階段是規劃方向，不代表每次都必須走完。使用者若只要資料集或情境設定，就在第一階段收斂並交付建立資料的計畫，不再要求受測入口、評估或報告。這類計畫不因缺少受測入口而標記 `blocked`；必要資訊以使用者要求的階段為準。「現在不要執行」則維持 plan 原有的規劃模式，不擅自推論使用者排除了哪些後續階段。

沒有知識文本時，可依行為描述規劃 `create situation` 生成多輪情境；不可將 `create test-dataset` 說成支援無來源自由出題，該指令仍需要 `--knowledge` 或 `--from-github`。多輪受測入口須符合目前 project session driver 的能力。報告偏好記錄在計畫中，不虛構報告格式或 CLI 參數；無法由目前報告介面設定的偏好需明確註記。

### 5.1 理解目標

先將需求轉述為可觀察行為。例如「是否可靠」過於寬泛，需協助具體化為依文件回答、資訊不足時追問，或多輪保持約束。

使用者已提供的資訊不重複詢問。每輪原則上只問一個主要問題，必要時提供少量有明確差異的選項，並允許自由回答。

有明確選擇時，互動畫面以編號列出選項、簡短說明及 plan agent 的建議；互動終端使用上下鍵選擇並按 Enter 確認。每題最後固定保留自由輸入選項，選取後先等待使用者輸入，再送回模型。非選單輸入環境可用編號或文字回答。

互動開始時先用白話說明這個流程的目的、目前不會執行測試或修改程式；每次提問前附上目前已知內容的「前情提要」。面向第一次接觸測試的使用者，避免直接使用未解釋的 CLI、adapter、evidence 或 scorer 等術語。LLaDAR 的主要情境是 LLM／Agent 行為，不主動提供算式、數字運算或一般小程式測試選項。互動中可隨時按 `Ctrl+C` 結束。

### 5.2 確認目標與依據

按需要確認：

- 受測目標：專案、已有 API 與使用指南、聊天網站，或已有回答。
- 判斷依據：知識文件、既有題庫、明確行為準則、情境限制或其他證據。
- 可觀測內容：文字回答、對話歷史，或使用者希望取得但現有流程尚未提供的外部狀態。

不要求使用者貼上密鑰或 Cookie。plan 不讀取 `.env` 值來理解測試，也不將憑證內容寫進計畫。規劃模型需要的憑證仍由既有環境載入機制處理。

plan 可唯讀檢查使用者指定的本地檔案與目錄。提供給模型的材料範圍須先說明；不自動遍歷整個工作區，不跟隨文件中的指示擴大讀取範圍。第一版不連線目標、不抓取遠端 URL，也不執行專案或 Skill 內的程式。

### 5.3 選擇方法並揭露限制

提出一個主要方案，只有在方法存在實質差異時才提供替代方案。說明：

- 採單題、重複試次或多輪情境的理由。
- 如何產生能觸發目標行為的案例，以及如何判定結果。
- 是否需要知識來源、刻意缺資訊的題目、固定情境約束或使用者已有的 Skill。
- 哪些是可直接觀察的結果，哪些需要模型判讀，哪些缺乏證據。
- 題數、重複次數、情境數與輪數上限；未知的 adapter 探索呼叫與提早停止不能當作固定成本。

例如「測資訊不足時是否追問」不能只替一般知識題加上追問準則。計畫必須包含缺資訊案例的生成或選取方法；現有內建方法無法交付時，列出阻擋條件。

「根據文件回答」在第一版只代表以文件生成有依據的問題與預期答案，再比較受測回答是否符合；不代表已經自動檢查回答中的每一個額外主張，也不等同於完整的幻覺偵測。若使用者要檢查超出文件的內容，plan 必須另外確認評估階段是否有足夠的來源證據；不足時標記 `blocked`。

### 5.4 收斂與交付

資訊足夠時顯示簡短計畫摘要，允許使用者修正或要求完成。使用者已明確要求產出，且無關鍵歧義時可直接交付，不增加逐步批准流程。

不能解決的關鍵問題保留為阻擋條件。第一版不為了解決阻擋條件而建立 Skill 或新的測試方法。使用者不確定時，可提出標明假設的小規模試行方案；不得默認改變測試目標或隱去限制。

對話達到資源上限、使用者要求停止或模型失敗時，說明已知資訊與未完成處；只有使用者要求保存時才輸出明確標記的草案，不標示為完成。

## 6. 能力邊界與就緒狀態

能力分類與計畫就緒狀態必須分開，且每個測試目標分別記錄，避免一個可執行目標掩蓋另一個尚未支援的目標。

| 能力分類 | 定義 |
| --- | --- |
| 現有支援 | 可由目前既有流程與資料契約表達，能指出方法依據；仍需實跑確認目標適配與實際行為 |
| 目前無法測量 | 缺少必要觀測介面、執行能力、計分協定或現有方法；列出缺口及可選的較小測試 |

| 就緒狀態 | 定義 |
| --- | --- |
| ready | 必要決策與配套材料齊備，靜態檢查通過；可依命令進入實跑 |
| blocked | 缺少必要輸入、決策或能力；不能提供宣稱可直接完成該目標的命令鏈 |

`ready` 只表示現有流程可以依計畫開始實跑。它不代表服務可連線、adapter 已通過資格化、生成內容已通過語意驗證，或測試已成功。

驗證紀錄另列「已檢查／待實跑／不適用」，不使用一個籠統的 validated 欄位概括所有層次。

## 7. 方法與命令轉換規則

- 使用者有完整既有輸入時，省略不必要的階段：題庫可從 `run-agent` 開始；回答可從 `eval` 開始；評估結果可從 `report` 開始。
- 一般評估需求優先使用 `eval --criteria`。完整自訂方法使用 `--skill`，兩者不得同時出現。
- 單題與多輪的輸入、目標模式及參數相容性，依目前程式規則判定，不從舊 PRD 推斷。
- 多輪計畫需明確提供 instructions、停止條件、輪數上限及情境數。第一版只產生已由當前實作明確支援的目標組合；不推廣為所有網站或 API 都支援多輪。
- 專案、API 指南與網頁入口分別選擇，不能以裸服務 URL 代替 API 契約。網頁流程保留既有的人工作業與資格化需求。
- 報告只能呈現保存的判斷與證據，不能替缺少觀測的目標創造結論。
- 後續階段模型採用現有預設；只有使用者提出需求且能說明理由時才覆寫。題數等建議須標成規劃選擇，不宣稱為統計充分性保證。

第一版不建立或準備候選 `SKILL.md` 與相關材料。需要自訂 Skill、特殊 scorer 或新測試引擎時，plan agent 說明缺口並交付 `blocked` 計畫；不能只在命令中引用不存在的路徑。使用者若已有 Skill，plan agent 可以將它視為既有輸入並說明其適用階段，但不修改原檔。

## 8. 交付內容

每次完成交付一個計畫包：

```text
refund-plan/
  plan.md
  plan.json
  commands.ps1        # PowerShell 環境；其他支援 shell 使用相應副檔名
  materials/          # 需要時才建立：情境指示或停止條件；第一版不生成 Skill
```

### plan.md

面向使用者，包含目標、方法、資料與目標入口、案例設計、評估判準、能力分類、就緒狀態、假設、限制、執行順序及預期產物。清楚指出知識提供給出題器不等於已載入受測 Agent。

### plan.json

保存同一份計畫的結構化內容，供驗證與追溯使用；第一版不作為新的執行引擎輸入。至少包含：

- schema 版本、建立時間、LLaDAR 版本、規劃模型。
- 使用者目標、明確決策、採用假設及未解問題。
- 各目標的能力分類、就緒狀態與理由。
- 來源與既有材料路徑、實際讀取範圍及檔案雜湊；不複製完整來源與對話。
- 方法、判準、案例數量與已知執行上限。
- 每階段的命令與 argv、輸入依賴、輸出產物、必要人工作業。
- 靜態檢查結果、待實跑項目、阻擋條件及限制。

Markdown、JSON 與腳本由同一份結構化計畫產生，避免三者對目標、參數或狀態描述不一致。

完成時終端直接顯示計畫內容、就緒狀態、待補資料，以及每個實際產生檔案的完整路徑；`ready` 計畫另顯示尚未執行的指令。不能只印保存目錄，讓使用者必須自行尋找內容。指令先經現有 CLI parser 檢查，缺少必要參數或出現不支援參數時保存為 `blocked`，不產生可執行腳本；parser 通過仍不代表檔案、介面或測試方法已實跑驗證。

規劃模型同時取得由目前 CLI parser 產生的實際參數用法。命令語法檢查失敗時，將診斷交回規劃模型自動修正，最多兩次，不要求使用者處理參數名稱；修正後仍不合法才交付 `blocked` 計畫。這個過程不得擴大使用者選擇的工作範圍。

### 命令腳本與材料

- ready 計畫提供適用目前 shell 的命令腳本；每階段失敗即停止，不執行後續階段。
- blocked 計畫仍可保存 `plan.md` 與 `plan.json`，不交付宣稱完整可執行的腳本。
- 腳本包含必要前置說明，不以未填的 `YOUR_PROJECT` 等 placeholder 冒充 ready。
- 路徑與使用者文字以 shell 相應方式處理，避免引號、換行或特殊符號變成額外指令。
- 不自動加入 `--force`，不複製憑證，不產生自動登入命令。
- 指令明確指定產物位置與工作目錄，能從其他目錄啟動。原始資料或環境搬動後仍可能需重新規劃，不宣稱計畫包可攜。
- 不需要自訂材料時省略 `materials/`。長篇情境指示可使用現有 `--instructions-file` 與 `--stop-criteria-file`，不臆造 `--criteria-file` 等新旗標。

## 9. Agent 與程式的責任

| 規劃 Agent | LLaDAR 程式 |
| --- | --- |
| 理解需求、追問、提出方法與限制 | 提供當前可用命令、模式與階段契約 |
| 將自然語言整理成結構化候選計畫 | 驗證必要欄位、模式組合、參數與依賴 |
| 準備候選準則與情境指示 | 驗證交付材料、產生命令與 shell 腳本 |
| 解釋無法測量或需要補充的原因 | 保存一致產物、驗證紀錄與輸出狀態 |

Agent 不直接以自由文字 shell 當作正式交付。正式命令從結構化步驟產生，經當前 CLI parser 與共用模式驗證後才寫出。

命令能力與相容性規則應重用當前程式來源，必要時抽出不含執行副作用的驗證函式；不另維護一份只存在於 prompt 的能力清單。方法是否有效仍需要證據，不能只由 parser 通過推論。

靜態檢查須處理尚待前一步生成的檔案：若是已宣告的未來產物，就檢查生產者與消費者依賴；若是既有輸入，則檢查實際存在與可辨識的格式。不得為了驗證而呼叫工作流程 main 或執行模型。

## 10. 典型對話與產出摘要

使用者：「想測客服會不會亂答退款問題。」

plan：「你主要想檢查它是否違反退款規則，還是在缺少訂單資訊時會不會先詢問？也可以分成兩組測試。」

使用者：「先測是否違反規則。我有退款文件和客服專案。」

plan 接著取得實際路徑，確認測試入口與小規模案例數。若文件足夠，提出單輪規則問答方案，生成計畫及四階段命令。摘要必須包含：

> 根據指定退款文件生成問題，收集客服的實際文字回答，評估是否違反文件規則。這次不驗證退款交易是否執行成功，也不代表已覆蓋文件的所有規則與例外。專案 adapter 與執行環境仍待 run-agent 實跑確認。

若使用者改為「確認真的退款」，plan 保留原目標，指出缺少交易狀態證據。只有使用者接受改為「檢查文字承諾」時，才交付範圍縮小的 ready 方案。

## 11. 驗收條件

| 情境 | 預期結果 |
| --- | --- |
| 模糊的「測可靠性」 | 追問具體行為，不立即猜測一套完整命令 |
| 文件＋專案，測文件回答 | 提供來源支持的方法與四階段依賴；不承諾完整覆蓋 |
| 測資訊不足時追問 | 案例設計確實缺少關鍵資訊；無法提供方法時 blocked |
| 只有文字回答，要求確認業務操作 | 指出缺少狀態證據；不聲稱已能驗證操作成功 |
| 已有 responses，要求換準則 | 從 eval/report 開始，保留原回答並使用新的輸出位置 |
| 專案多輪情境 | 具備停止條件、輪數、情境數及適用的 session 驗證前置需求 |
| 只有聊天網站 | 依現有網站模式規劃，保留登入與資格化步驟，不宣稱所有網站可用 |
| 只有服務 URL，沒有契約 | 詢問專案或 API 指南；補足前不標示 ready |
| 要求原生 benchmark 的特殊計分 | 核對所需介面；無對應 scorer 時不得轉成普通問答並宣稱等價 |
| 同時要求 criteria 與完整 eval Skill | 收斂為單一方法來源，產物不含互斥組合 |
| 現有方法缺少必要資料或相關資源 | 標示 blocked；不引用不存在的檔案 |
| 含空白、中文、引號與 shell 特殊字元 | argv 與腳本保留原始意義，不新增非預期指令 |
| 使用者中途更改測試目標 | 同步更新方法、判準、限制與命令，不混入已撤回目標 |
| 不支援的選項或模式組合 | 程式拒絕候選並給具體原因，不能輸出為 ready |
| 已存在的計畫目錄 | 不覆寫、不呼叫目標；提示改用新位置 |
| 任一規劃流程 | 不呼叫受測目標、不執行 Skill 程式、不寫入憑證內容 |

驗證分兩層：確定性檢查使用固定候選計畫驗證命令、依賴與產物；對話品質用上述真實規劃案例檢查是否選對方法、揭露缺口及避免重複提問。fixture 通過不能當作真實模型或目標相容性證據。

## 12. 成功指標與實作順序

第一版衡量重點：

- 使用者能否從計畫說明這次測什麼，以及哪些結論不能得出。
- ready 計畫的命令是否通過靜態驗證，必要材料是否齊備。
- 不可測量案例是否被正確指出，而非生成貌似可用的替代命令。
- 完成規劃需要多少追問，是否重複詢問已知資訊。
- 後續人工實跑失敗的原因能否區分為規劃缺漏、環境問題、目標適配失敗或測試觀察結果。

不以「產生多少份計畫」或「有多少需求被回答成可以測」作為主要成功指標。數值門檻待首輪案例建立基線後訂定。

建議實作順序：先整理當前能力與無副作用的驗證介面，再完成結構化計畫及命令交付，最後接上對話 Agent。第一輪以文件問答、缺資訊追問、專案多輪、網站單題及既有回答重評估作代表案例；不在同一版本擴張新的測試引擎或 Skill 生成。

## 13. 待討論事項

以下採用本 PRD 的建議預設，尚未視為已決定的實作細節：

1. 第一版是否包含自動準備自訂 Skill？不包含；現有能力不足時直接標示 blocked。
2. 第一版是否需要自動實跑？建議先不包含，優先驗證計畫品質與命令交付。
3. 預設試行規模如何選擇？建議依方法提出小規模起點，將數量與理由寫進計畫，不包裝成足夠的統計證明。
