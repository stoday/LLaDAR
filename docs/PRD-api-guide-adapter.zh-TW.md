# 文件驅動 API Adapter：`--service-url` 與 `--api-guide`

- 日期：2026-10-16
- 狀態：ready-for-agent
- 追蹤：[GitHub Issue #20](https://github.com/stoday/LLaDAR/issues/20)
- 基準：LLaDAR v0.12.0；本規格定義 API 文件模式的新功能。
驗收範圍：已確認 CLI／獨立 adapter 實際 HTTP 呼叫、四種文件格式、缺漏契約、續跑，以及 PDF 無可用文字時直接報錯。

## Problem Statement

使用者有可呼叫的 Agent API，以及描述 API 使用方式與範例的文件，但不一定取得專案原始碼。目前既有服務的 adapter 生成與匯出依賴 `--project` 與專案探索，單獨提供 `--service-url` 無法建立完整的呼叫契約。

使用者希望直接指定 API 文件，由 LLaDAR 理解如何送出 Question record 的問題、取得目標 Agent 的 Actual response，並產生可獨立執行的 adapter。使用者不應為了提供 API 契約而建立假專案或準備目標專案的虛擬環境。

API 使用文件提供的是呼叫與 Answer extraction 的依據，不是回答問題的知識來源，也不是 Expected answer。文件或模型推論不能被當成實際呼叫已成功的證據。

## Solution

新增 `run-agent` 的文件驅動 API 模式：使用者同時提供 `--service-url` 與 `--api-guide`，不需要 `--project`。

支援單一文件的 `.txt`、`.md`、`.docx`、`.pdf`。DOCX 讀取本文與表格；PDF 只擷取既有文字並保留頁碼，不使用 OCR。無法讀取、損毀、無可用文字或契約不足的文件，必須清楚報錯，不能繼續猜測端點或生成看似成功的 adapter。

正常流程為：

1. 檢查參數與讀取文件。
2. 依文件擷取 API 契約，保存可回查的來源依據。
3. 生成呼叫既有服務的 Python adapter。
4. 在空工作目錄與隔離 Python 中，經實際 HTTP 呼叫驗證請求、答案擷取與完成條件。
5. 驗證成功後，依既有排程執行資料集，保存 Actual response 與各次 Trial。
6. 共用現有交付流程，產生 `adapter.py`、README 與附說明的 `.env.example`。

`--service-url` 是實際服務的位址。文件中的範例網址用於辨識相對路徑，不能覆寫使用者指定的服務。認證方式由文件說明，正式憑證來自使用者的環境變數或 `--env-file`。

## User Stories

1. 身為只有 API 文件的使用者，我希望不提供專案原始碼也能執行資料集，以便測試外部 Agent。
2. 身為 CLI 使用者，我希望以 `--service-url` 搭配 `--api-guide` 選擇文件模式，以便清楚指定服務與契約來源。
3. 身為 TXT 文件使用者，我希望讀取文字與程式碼範例，以便沿用現有 API 使用說明。
4. 身為 Markdown 文件使用者，我希望保留標題、程式碼區塊與範例的關係，以便正確理解請求與回應。
5. 身為 DOCX 文件使用者，我希望本文與參數表格都被讀取，以免遺漏認證、必要欄位或回應格式。
6. 身為 PDF 文件使用者，我希望讀取可選取的文字並保留頁碼，以便回查 API 契約的依據。
7. 身為掃描 PDF 使用者，我希望無可用文字時立即收到錯誤，以免程式默默進行 OCR 或猜測文件內容。
8. 身為提供損毀、加密或不可讀文件的使用者，我希望得到格式及原因明確的錯誤，以便更換可讀文件。
9. 身為文件撰寫者，我希望缺少必要使用說明或範例時列出缺漏，以便補齊文件後重試。
10. 身為提供多個 API 範例的使用者，我希望只選擇有完整文件依據的呼叫流程，以免呼叫無關端點。
11. 身為非互動執行的使用者，我希望契約有歧義時停止並提供說明，以免程式自行選擇不確定的流程。
12. 身為測試服務使用者，我希望實際呼叫只使用我提供的服務位址，以免文件中的示範或正式環境網址被直接使用。
13. 身為需要認證的使用者，我希望 adapter 依文件使用我自己的環境變數，以便保留原有認證方式。
14. 身為分享 adapter 的使用者，我希望交付包不包含我的憑證或私人文件內容，以便讓接收者使用自己的設定。
15. 身為資料集使用者，我希望問題確實送到目標 Agent，以免把文件範例或 LLaDAR 自行生成的內容當成回答。
16. 身為回應格式包含其他欄位的使用者，我希望只擷取文件指定的完整答案，以免把進度、診斷或錯誤當成 Actual response。
17. 身為使用串流或輪詢服務的使用者，我希望依文件的完成條件取得完整答案，以免只保存部分回應。
18. 身為遇到 HTTP 錯誤的使用者，我希望得到可辨識的失敗紀錄，以便修正認證、服務或契約。
19. 身為遇到逾時或中斷的使用者，我希望保留工作階段並能續跑，以免重複已完成或完成狀態不明的呼叫。
20. 身為修改 API 文件的使用者，我希望續跑時能偵測文件變更，以免混用不同版本的契約。
21. 身為重用既有 adapter 的使用者，我希望在文件模式中也能驗證它，以便避免不必要的重新生成。
22. 身為交付 adapter 的使用者，我希望它可離開原工作目錄獨立執行，以便在另一台電腦呼叫相同服務。
23. 身為繁體中文使用者，我希望交付 README 與設定說明遵循 `--lang zh-TW`，以便接收者容易理解。
24. 身為使用其他語言的使用者，我希望沿用現有文件自動翻譯與快取，以免每種語言另寫模板。
25. 身為長時間等待的使用者，我希望看見文件讀取、契約擷取、驗證與執行階段，並可按 Enter 查看目前活動。
26. 身為 Windows、Linux 或 macOS 使用者，我希望文件模式與獨立 adapter 都能在我的系統運作。
27. 身為既有專案或瀏覽器模式使用者，我希望新增文件模式後原有指令仍然有效。
28. 身為評估結果的讀者，我希望回答與執行證據仍使用現有資料契約，以便後續 Evaluation plan、Judgment 與 Report 不需另寫流程。

## Implementation Decisions

### 模式與參數契約

- 在既有 `run-agent` 入口增加 `--api-guide`，公開 Python 執行介面提供對應的 `api_guide` 參數。
- 文件模式必須同時提供 `--api-guide` 與 `--service-url`。缺少其中一項必要資訊，在呼叫模型或 API 前報錯。
- `--api-guide` 與 `--project`、`--page-url` 互斥，也不能與直接供應回答的執行模式混用。文件模式不得默認改用目前目錄作為目標專案。
- `--project` 的既有服務與受管理服務模式，以及 `--page-url` 的瀏覽器模式，保持其既有選擇規則。
- 第一版適用單題資料集協定；多輪 Situation config 模式不在本規格承諾範圍。若搭配多輪參數，應在任何模型或 HTTP 呼叫前明確拒絕。
- `--api-guide` 第一版接受一個本機檔案，不接受目錄、文件網址或多份文件合併。副檔名不分大小寫。
- 文件模式沿用既有 adapter 模型、模型設定、等待時間、工具及模型呼叫預算；不新增不受限的自動探索或修復迴圈。

### 文件讀取與可回查依據

- 使用獨立的 API 文件讀取模組；不把 API 文件混入知識生成或評估知識來源。
- TXT 與 Markdown 支援 UTF-8 與 UTF-8 BOM。解碼錯誤不能以替換字元默默繼續，必須說明無法讀取。
- DOCX 擷取依文件順序可取得的本文與表格文字，保留段落及表格儲存格的來源定位。純圖片內容不宣稱已讀取。
- PDF 沿用已存在的 PDF 文字讀取能力，按頁保留文字與頁碼；不啟動 OCR，也不將頁面影像送給視覺模型辨識。
- PDF 整份文件沒有可用文字時，報錯「無法讀取 PDF 的文字內容，請提供含可選取文字的 PDF，或改用 TXT、MD、DOCX。」並停止後續模型、API 呼叫與交付包生成。
- 損毀、加密且無法開啟、缺少檔案或不支援格式時，同樣停止並指出原因與支援格式，不靜默降級為空文件。
- 混合文字與圖片的文件只能使用成功擷取的文字。空白頁可略過但須記錄；若必要契約只存在圖片中，應以契約缺漏停止，不能推論已讀到圖片。
- 來源記錄至少保存文件格式、內容雜湊、讀取結果及可回查的片段定位。TXT／Markdown 使用行號；DOCX 使用段落或表格定位；PDF 使用頁碼與片段定位。
- 長文件採有界讀取或分段取用，讓契約擷取能回讀相關片段。截斷或未讀部分須被記錄，不能宣稱完整涵蓋。

### API 契約與文件充分性

- 文件至少必須讓系統確定 HTTP 方法、相對端點、認證要求或明示無認證、必要 header、問題如何放入請求、完整請求範例、回應範例、答案位置，以及成功／完成條件。
- 可由同一份明確範例推出欄位對應；不能為了完成契約而發明文件未描述的端點、必要參數、認證方法或答案欄位。
- 契約擷取共用既有 coding-agent 能力，但契約證據驗證須接受文件定位，不能要求文件偽裝成專案原始碼。重要契約欄位及所選流程須能回查來源。
- 有文字不等於文件充分。讀取成功但缺少使用說明、請求或回應範例，或無法確定問題／答案對應時，列出缺漏並停止，不進行猜測性的 HTTP 試探。
- 多個完整候選依既有互動選擇流程處理；非互動模式若無法唯一決定，應停止並給出可理解的歧義說明。
- 實際服務位址以使用者指定值為準，文件的網址不得替代它。請求路徑須相對於該服務，不允許任意切換到其他 origin。
- 認證沿用文件描述的合法流程，所需憑證由使用者環境提供。文件範例中的憑證值不能直接成為正式憑證或寫入交付包；不得把憑證值送入生成提示或輸出紀錄。
- 沿用既有 HTTP helper 的 URL 檢查、拒絕重新導向、認證失敗處理與有限等待。不得啟停使用者提供的既有服務。
- 支援既有 adapter 能力可表達的 JSON 回應、SSE 及 job polling。串流或輪詢必須具有文件依據的關聯與完成條件；不明確或無法在既有 runtime 表達時應列明不支援並停止。

### 共用執行與交付

- 專案與文件提供不同的契約來源；契約確認後，共用既有 HTTP adapter 生成、實際驗證、排程、回答保存與匯出流程。不得另外複製一套執行器。
- 文件模式不要求目標專案或目標專案虛擬環境，不執行專案複製或原始碼 Graphify。獨立 adapter 使用 Python 標準函式庫與既有隔離驗證方式。
- 在空工作目錄及不載入專案／site packages 的 Python 中，以實際 HTTP 請求驗證 adapter。文件範例、生成的程式碼或 HTTP 200 本身都不能替代驗證。
- 驗證至少確認問題映射、必要 header 與認證、對應目標請求的完整回應、答案擷取及錯誤分類。不能使用 Expected answer 修正或生成目標回答。
- adapter 驗證失敗時沿用有界修復；仍失敗則停止，不發布未驗證的交付包，也不把失敗當成正常回答。
- 正式執行沿用 Question record、Actual response、Trial 與現有附屬紀錄。執行失敗的 Actual response 仍為 null，詳細原因留在既有執行證據中。
- 在文件模式允許沿用 `--adapt` 重用獨立 HTTP adapter；仍須實際驗證，不改寫使用者提供的原檔。
- 自動匯出與自訂 `--export-adapter` 沿用現有行為；交付文件與註解遵循 `--lang`，共用既有翻譯及快取。
- 未指定輸出時沿用集中輸出目錄；明確輸出位置仍優先。原始文件、讀取片段、私有回應、憑證與續跑工作階段不得混入可分享交付包。

### 續跑、進度與失敗

- 工作階段保存所選文件與雜湊、已讀來源定位、已接受契約、adapter 驗證結果及正式試次狀態，讓 `--resume` 重用已確認工作。
- 續跑須恢復原輸出與設定；文件內容、契約或服務設定不一致時，依既有完整性規則拒絕混用，明確提示重新開始或提供相同輸入。
- 續跑不得重送已完成，或提交後完成狀態不明的正式請求；不能因文件模式新增而弱化既有恢復保護。
- 文件格式與讀取錯誤在模型與目標 HTTP 呼叫前失敗；契約不足可在模型擷取後識別，但必須在目標 HTTP 呼叫前停止。非互動歧義、中斷、HTTP／認證錯誤及執行失敗沿用現有 CLI 的分類與退出碼慣例。
- 進度可識別文件讀取、契約擷取、adapter 生成／驗證與正式執行；沿用 `--verbose`、Enter 狀態查詢、`--log` 與人工提示交接。
- 進度、日誌及錯誤不得輸出原始憑證、完整私人 URL 或未遮罩的認證回應。失敗時不得顯示成功工作摘要或宣稱 API 已驗證。

## Testing Decisions

主要驗收 seam 為既有 `run-agent` CLI 與公開執行介面；獨立 adapter 的對外協定為交付驗收 seam。文件讀取器需要小範圍測試，以涵蓋二進位格式、頁碼、表格與不可讀輸入；不測模型提示措辭、內部函式呼叫次數或私有模組拆分。

離線驗收可以使用固定的契約生成回覆以穩定模型變因，但 HTTP 傳輸、服務端請求接收、回應擷取與獨立 adapter 執行必須真實發生。既有 portable adapter、HTTP 認證／重新導向、工作階段恢復、CLI 輸出，以及三平台狀態測試可作為先例。

### 必要驗收案例

1. **完整文件到正式回答**：在沒有目標專案或目標虛擬環境的目錄，以完整指南呼叫本機真實 HTTP server；核對服務收到資料集問題、方法、路徑、必要參數與認證，並保存其真正回傳的 Actual response。
2. **四種格式等價**：同一份契約分別製成 TXT、Markdown、DOCX、可選取文字的 PDF；四者皆能完成相同請求及答案擷取，且各自的來源定位能回查。
3. **DOCX 表格**：將必要欄位與答案位置放在表格中，確認成功；純圖片說明不能被算作已讀證據。
4. **PDF 不做 OCR**：以無文字的掃描 PDF 執行，確認清楚報錯、非零退出、零模型／目標 API 呼叫，且沒有交付包或成功摘要。不依賴任何 OCR 可執行檔或視覺模型。
5. **混合 PDF**：包含空白或圖片頁但其他文字已充分描述契約時可成功；必要資訊只有圖片時，以契約缺漏停止，不宣稱已讀取該頁圖像。
6. **不可讀輸入**：缺少檔案、損毀 DOCX／PDF、無法開啟的加密 PDF、空文字、錯誤編碼與不支援格式，皆在後續模型／HTTP 呼叫前失敗。
7. **文件充分性**：分別缺少請求範例、回應範例、認證說明、問題欄位、答案位置或完成條件；核對缺漏說明與零猜測性請求。
8. **模式衝突**：文件模式缺少服務網址、混用專案／瀏覽器／直接回答／多輪參數時，在任何模型或目標執行前拒絕；既有有效指令仍通過。
9. **服務位址覆寫規則**：文件範例使用其他 host，服務端只在使用者指定網址收到請求；不能啟停它，也不能追隨重新導向到其他 origin。
10. **認證與錯誤**：覆蓋必要憑證缺漏、有效認證、401／403、其他 HTTP 錯誤、連線失敗、逾時與錯誤回應格式；檢查有限等待、失敗紀錄及秘密值不外洩。
11. **回應完成語意**：JSON 取指定欄位；SSE 或 polling 僅依文件完成條件交付完整且關聯正確的答案。僅 HTTP 200、非空進度片段或未完成回應不得通過驗證。
12. **文件不代答**：範例答案與 Expected answer 使用不同於服務答案的內容，確認 Actual response 只來自真正的目標回應，沒有以模型補寫或修正。
13. **歧義與非互動**：多個完整候選需經既有選擇流程；非互動模式歧義時停止，服務端沒有收到未授權試探。
14. **獨立交付**：將交付包搬到空目錄，以隔離 Python 執行；確認不依賴 LLaDAR、指南或目標專案，能使用接收者自己的服務設定及憑證。
15. **文件語言**：確認 README 與設定註解遵循 `--lang`，程式碼及參數名稱不被翻譯，憑證值為空，接續執行可重用翻譯快取。
16. **中斷與續跑**：在契約確認、adapter 驗證與正式試次階段中斷，確認恢復原輸出、不重做已接受工作、不重送已完成或完成狀態不明的正式請求。
17. **文件變更與完整性**：續跑時修改指南或破壞 checkpoint，確認拒絕混用；同一內容的正常恢復仍成功。
18. **adapter 重用**：重用通過驗證的獨立 adapter，原檔保持不變；驗證失敗時停止，不冒充已修復。
19. **進度與清單**：完成摘要列出實際回答、試次、工作階段及交付包；`--log` 可保存階段訊息，JSON stdout 與人工提示仍保持原協定。
20. **作業系統**：Windows、Ubuntu、macOS 原生 CI 覆蓋格式讀取、CLI、實際 HTTP 呼叫與獨立交付；沿用既有終端狀態與輸入交接驗收。

需要外部真實模型或外部 API 的額外驗證應明示條件與成本，不能以缺少憑證為由把上述離線外部行為案例變成空驗收。

## Out of Scope

- OCR、掃描文件辨識、圖片／視覺模型讀取、PDF 自動解密，以及承諾讀取所有 PDF 排版。
- `.doc`、圖片、試算表、文件網址、自動抓取網站或多份文件合併。
- 沒有文件依據的 API 探測、自動建立後端、修改 API、繞過認證或新增測試路由。
- 把 API 指南當知識庫、Expected answer 或生成 Actual response 的來源。
- 文件模式的多輪 Situation config、WebSocket、瀏覽器登入或瀏覽器 fallback。
- 匯出原始指南、真實憑證、登入狀態、目標專案或續跑資料。
- 改寫既有專案／瀏覽器模式，或另建一套評估與報告流程。

## Further Notes

文件模式用法：

```powershell
lladar run-agent dataset.jsonl `
  --service-url https://example.com/api `
  --api-guide api-guide.docx `
  --env-file .env `
  --lang zh-TW
```

文件可替換為 TXT、Markdown 或含可選取文字的 PDF。未指定輸出時，結果與附屬檔沿用 `runs/` 的集中存放規則；可用既有輸出及匯出選項自訂位置。

本規格延伸既有服務的 HTTP-first 與獨立 adapter 契約：文件決定如何呼叫，實際執行決定是否驗證成功。狀態名稱、失敗分類、預算與語言處理應沿用現有公開契約，不另加一套語意。
